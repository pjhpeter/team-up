# team-up：Herdr 需求交付流程

**这是什么**：一套让多个 AI Agent 按「方案 → 开发 → 评审 → 测试 → 上线」接力交付 GitLab 需求的流程。规则、脚本、角色配置都在这里，本机的 `~/.hwf` 就是本仓库的副本。

## 装到一台电脑上

```sh
git clone git@git.bootingai.net:ai-hub/skills/workflow/team-up.git ~/.hwf
sh ~/.hwf/install.sh
```

然后让每个要用流程的仓库接入一次（先不加 `--apply` 看一遍要做什么）：

```sh
python3 ~/.hwf/scripts/init-project.py ~/code/<仓库> --apply --smoke "国内=https://<测试环境地址>"
```

## 里面有什么

| 位置 | 作用 |
| --- | --- |
| `PROTOCOL.md` | 短入口：共同边界、阶段路由、按需阅读与规则维护方式 |
| `protocol/` | 七个主题：调度、沟通、规划、实现、评审测试、交付、工作树；进入对应阶段时再读 |
| `skills/` | 成员干活的具体做法（install.sh 链接到 `~/.agents/skills/` 和 `~/.claude/skills/`，不走团队流程时也能用）：`acceptance-test-cases` 写和评测试用例，`test-first-evidence` 测试先行留证与实现前核验，`scoped-code-review` 限定范围的代码评审与回改核验，`real-browser-acceptance` 真实浏览器或桌面验收、过程录屏与附件上传、服务清理。协议管何时做、谁做、出口，skill 管怎么做 |
| `workflows/team-up.yaml` | Herdr 启动团队的入口 |
| `herdr/config.yaml` | 各角色用什么工具、什么模型（install.sh 把 Herdr 插件配置链接到这里） |
| `herdr/droid-arch.json` | 架构师（droid）的模型与思考档；交互式 droid 只能用 `--settings` 文件指定 |
| `member-omp.yml` | 成员的 omp 上下文压缩设置（约 20 万词元压缩；目前没有角色使用） |
| `scheduler-omp.yml` | 调度者的上下文压缩设置 |
| `scripts/` | 收件箱、飞书桥、找调度者、按角色领取成员、给调度者 tab 起名、成员收尾、上传方案和测试用例为 snippet 并回读核对（`upload-snippet.py`）、统一轻量录屏（`test-record.py`：网页 `ego-browser` 与 Electron 单窗口输出 `.mp4`）、测试录屏与截图上传 GitLab 附件并回读核对（`upload-media.py`）、任务记录与评论（`task-record.py`：写 INDEX 行、STATE 顶部、按通知模式发评论、请用户同意前自查权限、核对架构师的需求理解卡是否写全、核对汇总分支完整性 `release-check`）、交付收尾（`wrapup.py`：关成员、删 worktree、发收尾回执、写 INDEX）、清理临时目录、新项目接入等脚本 |
| `templates/project/` | 新项目接入时写进仓库的文件模板 |
| `omp-extensions/` | omp 扩展：调度者手改 INDEX 或直接用 glab 发 issue 评论时拦下，要求改用 `task-record.py`（install.sh 链接到 `~/.omp/agent/extensions/`） |
| `tests/` | 脚本的单元测试，CI 每次推送都跑 |
| `gitlab-inbox.config.json` | 收件箱共用配置：盯哪些 GitLab 项目、只认谁的操作、开关标签、轮询间隔；`proactive` 段是主动接活用的模型 |
| `proactive-rules.md` | 主动接活的规则：什么情况 → 做什么，每条规则单独一档 |

不入库（每台电脑自己的）：`state/`（运行状态）、`gitlab-inbox.local.json`（每个项目在本机的仓库路径，也可覆盖共用配置里的其他值，比如换成你自己的白名单账号）。

收件箱要常驻在一个 Herdr 窗格里：`python3 ~/.hwf/scripts/gitlab-inbox.py`；相关脚本更新后空闲时会自动热重载，改了配置则在那个窗格按 Ctrl+C 再重新运行。

## 从飞书提需求（可选）

接上之后，私聊直接说想做什么，群里 @机器人后直接说，不必记住「需求：」前缀。每条自然消息统一判断“要做什么、针对哪张任务、是否已经授权”，再核对目标并执行，避免不同入口重复判断或误建单。模型可以理解任务名称和本次会话里的指代；目标不清楚时先问，不默认新建或随便选一张。私聊通知保留秘书主窗口单出口；群聊保留群内回复，Agent 团队通过 GitLab 推进交付。

| 在飞书里发 | 结果 |
| --- | --- |
| 「给文件列表加一个按时间筛选」 | 建需求单，先进入正常分析与确认流程 |
| 引用问题说「帮我修复这个 bug」 | 带引用建单，进入修 bug 流程；已有任务不重复建单 |
| 回复机器人关于某个任务的说明，说「先暂停测试」 | 转交原任务，不另建 issue；引用目标不明确时先问清楚 |
| 「让 484 先停止测试，测试环境在维护」 | 转交 #484，不把暂停指令当成新需求，也不发开工命令 |
| 「画布同步那个先别测了」 | 从可见任务中辨认名称；唯一确认后原文转交，多个相似任务先问清楚 |
| 「刚才那个继续」 | 参考本用户在当前会话里谈过的任务；跨群、过期或多个目标不能猜 |
| 「进度怎么样」与「告诉负责人先别改」 | 前者只回答，后者转交指令；引用和历史不能代替本次开工授权 |
| 「修一下这个」但没有可用上下文 | 问缺少的信息，后续回答继续这次请求，不要求重发固定格式 |
| `需求：<内容>` 或 `/需求 <内容>` | 建 issue（打 `herdr-auto`、指派给 Agent），回帖 issue 链接 |
| `#123 <内容>` 或贴 issue 链接 | 把这个话题关联到已有 issue，内容写成评论 |
| 在上面的话题里回复 | 统一区分问题、补充和执行指令；`/go`、`/status` 等显式命令照常生效 |
| 调度者贴出编号选项后回一个数字（如 `1`） | 收件箱核对界面没变，替你在电脑上选中这一项并回帖结果 |

引用群消息再 @机器人说要做什么，建单会带上引用文字和附件；关联已有 issue、话题内引用回复和私聊转达也使用同一套收集逻辑。引用内容只作背景，不能代替用户本次授权。已带入的话题前文和附件去重，纯 `/go` 等指令不混入引用内容。引用读取失败会在 GitLab 内容中注明缺失，不静默省掉。

群里给机器人下指令时，每句话（包括话题里的回复）都要 @机器人；私聊不用。白名单外的人找机器人，它从 10 句俏皮话里随机回一句（如「给钱我主人，我帮你干活」），什么都不做。

图片或文件可以和文字一起发送，也可以先发附件再说明要做什么；自然语言和显式命令都能带附件。识别服务失败会明确提示「处理失败」，保留原请求供回复「重试」，不会让用户反复补已经给出的编号，也不会擅自转给引用中的另一张任务。真正缺少目标或内容时才追问。飞书桥相关脚本更新后会在队列空闲时自动热重载；改了本机配置则需要在原来的窗格按 Ctrl+C，再运行 `python3 ~/.hwf/scripts/feishu-bridge.py` 才会生效；之前已回复过的消息不会自动重试。

从一个需求拆出独立 issue 时，各自使用独立飞书话题：原话题只留新话题链接，结果、录屏/截图和确认各归各。调度者按 `protocol/communication.md`「独立需求与飞书话题」登记并核对建立结果；原话题不会因提到别的编号而切换绑定。`/status` 读取对应 GitLab issue 的当前状态；普通「已收到」回执只代表已转交，不代表执行或交付完成。

### 私聊即秘书：多个需求统一跟进

同时跑的需求一多，挨个话题去看会顾不过来。和机器人的私聊窗口就是秘书，不用开启命令：你在私聊里说过一句话，机器人就记住这个窗口。

| 秘书做什么 | 说明 |
| --- | --- |
| 马上转达 | 调度者发出的每条实质评论马上转到私聊，开头写「#编号 标题」；默认免打扰由调度者执行：纯进度只记任务记录，步骤完成、整项完成、新风险、用户待办或实质答复才通知 |
| 避免重复 | 私聊绑定只发到秘书主窗口，原话题保留回复入口与历史；固定「已收到」转交回执不重复转，调度者不追加纯确认；群聊仍保留群内回复 |
| 每小时巡检 | 有变化或异常（等你处理、已待上线但调度者没 @你 请求授权合并、调度者卡住或退出、超过 3 小时没动静）才汇报，没变化不发 |
| 快速回复 | 对某条转达点「回复」，机器人知道你指的是哪张任务；提问就回答，指令或补充才转交，`/go` 等显式命令仍可直接发 |
| 替你传话 | 说「告诉 484 和 488，测试环境已恢复，继续工作」，秘书分别在对应 issue 下 @Agent 留言，并合并回报每项结果；不同任务的指令分别转交，不会混发。部分未完成可回复「重试未完成项」，已成功项不会重复发送；发送结果不明时先核对任务评论，不盲目重发 |
| 回答提问 | 发「进度」看总览，发「帮助」看用法；自然任务走共享识别入口，其余提问按总览、各需求最近评论和最近转达回答。识别复用秘书的模型配置（`feishu-bridge.local.json` 的 `secretary.model`、`thinking`） |

「需求：…」、`#编号` 和 `/go` 仍是快捷方式，不是必填格式。各需求自己的话题照常保留（默认免打扰），想看某个需求的完整经过去话题里看。自然语言开工不包含上线、合并 main 或其他原本需要单独授权的操作。

模型返回一个可校验的决定：新任务、转交已有任务、批量转交、回答或追问，并附目标来源和对应的用户原话。批量指令先完整校验，再逐项执行和保存结果；只要有目标或正文校验不通过，整批不执行。代码检查目标确在本会话可用范围内、来源与原话对应，不靠暂停/继续等关键词分流，也不依赖模型自报的“置信度”。明确的多个目标自动拆分，只有目标、内容或授权确实不清楚才澄清。

每人接一套：用 lark-cli 建好机器人应用、存一个本人 GitLab 令牌、写本机配置 `~/.hwf/feishu-bridge.local.json`，然后在一个 Herdr 窗格里常驻 `python3 ~/.hwf/scripts/feishu-bridge.py`。完整步骤、用法和排查见 Wiki [飞书接入](https://git.bootingai.net/ai-hub/skills/workflow/team-up/-/wikis/飞书接入)。

## 主动接活（observe 档）

没人叫 Agent 时，收件箱每 10 分钟看一遍 GitLab 新开的 issue（创建满 2 小时仍没人指派的）和 main / release-* 失败的流水线，再加上飞书「观察群」里的对话，按 `proactive-rules.md` 逐条判断 Agent 本来该不该主动接活。observe 档**只记录、不动手**：对 GitLab 只读，不在飞书说话，不启动调度者。

| 要做的事 | 怎么做 |
| --- | --- |
| 看观察结果 | `python3 ~/.hwf/scripts/proactive.py report`（生成报告并打开；每条右侧有标注命令） |
| 标注判得对不对 | `proactive.py mark O-0031 ok`、`mark O-0032 wrong 理由`（理由写「严重」算严重误接）、`mark O-0040 should R2 理由`（漏接） |
| 改了规则验证一下 | `proactive.py replay R2 --days 14`：拿旧事件按新规则重判，对照之前的标注，不改原记录 |
| 加观察群 | 机器人要有飞书权限 `im:message.group_msg`；在 `feishu-bridge.local.json` 加 `"observe_chats": {"oc_xxx": "群名"}`，重启飞书桥 |
| 放开一条规则 | 成绩卡显示「可以考虑切 auto」后，由人把该规则的档位改掉（auto 档还没实现，现在按 observe 处理） |

平时不推送；每天 18 点后当天有新的「本来会接」时发一条 ntfy，当天判不了的事件超过 5 个时也发一条。记录都在本机 `state/proactive-*`。观察群里的图片会下载到本机、判断时一起给模型看（每段对话最多 4 张；文件和视频只记名字不下载），聊天原文和图片 7 天后自动删除；图片每小时检查一次，总量超过 300MB 就从最旧的开始删。搬到 GitLab 的附件上传完立刻删，飞书桥启动时还会清空中转目录。

## 怎么改

1. 在 `~/.hwf` 里建分支：`git switch -c <改什么>`。
2. 按 `PROTOCOL.md`「规则维护方式」修改对应条款，不追加事故流水账；workflow 用 loader 校验，脚本只跑直接相关的测试文件或用例。
3. 推送并开 MR，合并后其他电脑 `git -C ~/.hwf pull` 即生效（改了 `herdr/config.yaml` 且不是本人电脑的，再跑一次 `install.sh`）。

协议入口、主题和 skill 在本机更新后，下次读取时生效；收件箱监听 `PROTOCOL.md`、`protocol/` 与 `skills/` 的提交变化并提醒在途调度者。新增 skill 后要再跑一次 `install.sh` 才会链接到各 Agent。常驻的 `gitlab-inbox.py` 与 `feishu-bridge.py` 检测到自身及依赖模块变化且语法检查通过后，会在空闲时自动重新加载（窗格打印 `hot-reloading ...`）；修改本机 JSON 配置仍需在原窗格重启相应进程。
