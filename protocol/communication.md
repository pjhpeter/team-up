# 沟通、通知与收件箱

用户需要看到的是结果和待办，不是每次派活的流水。调度者统一对外发布，区分阶段结果与完整交付；事实和证据留在任务记录，需要用户处理时再明确通知。

## 沟通边界

- 成员只向调度者交付和提问，不直接向用户发消息、弹通知、要求操作，不在 GitLab issue/MR 评论或改状态（仅 test 可用 `scripts/upload-media.py` 静默上传本轮录屏/截图附件换取链接交调度者汇总），不发送 ntfy。调度者收取后统一发布、回读；成员报告阻塞不替代调度者通知。
- 调度者先查能否由已有授权或成员解决阻塞；可继续的授权工作照常推进。需要用户动作或实质答复时按下节，不以“成员问了”直接转成用户待办。用户启动交付流程（含 `/go`、debug/极简模式）即包含以下常规执行动作，团队直接按对应章节自理，**严禁发 `todo` 向用户请示或要求二次确认**：
  1. 创建、复用与推送 `release-<根编号>` 汇总分支、开发分支及冲突集成分支；
  2. 创建并合并指向 `develop`（`branches.test`）的测试分支 MR，以及冒烟通过后合入 `release-<根编号>`；
  3. 本地验收时在本 issue 独立 worktree 启动专属 Web 服务或开发版 Electron（受固定端口如 `3001` 约束时，核实端口空闲后直接启动、测完清理，不为“能否启动本地 Electron/Web”或“没有签名安装包”请示用户）；
  4. 可通过 `glab`、`git`、分支/MR/流水线状态或项目配置自行核实的客观事实（如评论已说明某分支/提交已合并或部署，直接查证，不再发评论请用户或同事确认）。
- 阶段通过不等于交付完成。详尽模式的阶段评论首句为「本轮<阶段>通过，整项需求尚未完成」，列剩余步骤、下一动作，再附原文与测试录屏/截图证据；明确本地、测试环境、生产环境和版本，本地 develop 模式不是部署成功。
- 尚待上线写清「尚未上线」，不提示可以关闭；最终验收、关闭请求及实际关闭事件按 [delivery.md](delivery.md) §9–§9.1 先核对证据，不把用户认可理解成放弃剩余工作。

## 通知模式

默认免打扰；详尽模式额外发布单阶段结果，但不降低任何证据要求。

| 时机 | 免打扰（GitLab / 飞书私聊） | 详尽（GitLab / 飞书私聊） |
|---|---|---|
| 新增/实质变化的用户待办、数据安全风险（`todo`/`risk`） | 写 GitLab 并立即推飞书私聊＋ntfy | 相同 |
| 用户问题或中途修改指令的实质答复、对话模式结论、`/status`（`answer`） | 写 GitLab 并立即推飞书私聊 | 相同 |
| 整项完成/最终验收请求（`delivery-done`） | 写 GitLab 一条汇总并立即推飞书私聊＋ntfy | 相同 |
| 每个步骤或子 issue 完成（`step-done`） | 只写 GitLab 一条汇总备查，**不推飞书私聊** | 写 GitLab 并推飞书私聊 |
| 已确认方案/已评审用例备案、待定清单、登记池（`record`）及正常收尾回执 | 只写 GitLab 存档备查，**不推飞书私聊** | 写 GitLab 并推飞书私聊 |
| 评审、本地测试、冒烟的单阶段结果（`stage`） | 只记 STATE，不发评论 | 发阶段评论（注明整项未完成）并推飞书 |
| 开工、切模式、清空上下文等纯命令回执 | 收件箱写 GitLab，**免打扰不推飞书私聊** | 推飞书私聊；调度者不重复确认 |

- STATE 顶部「通知模式」记录模式和来源；没写即免打扰。用户单独发送 `/免打扰`/`/quiet` 或 `/详尽`/`/verbose`，或在会话直接要求，即从收到起切换；收件箱回确认后调度者只改 STATE，不再确认，不补发或撤回历史评论。
- 正常流程的步骤汇总按 [delivery.md](delivery.md) §9 一次附评审、测试分支 MR/部署、release MR/SHA、待定项条数，以及折叠区**之外**的「验收标准逐条对账表」（每行含结果、播放器 `markdown`、起止时间段与 `/-/project/<数字ID>/uploads/...` 直链或免录原因）；步骤标题「步骤 <序号> 完成：<名称>」用 `--kind step-done` 写根 issue（不 `@用户`），整项汇总在 arch 最终验收通过后统一用 `--kind delivery-done` 发布（即使仍需等待用户点击合并或跨团队前置上线，也用 `delivery-done` 一次写清前置顺序与对账表，不用 `todo` 绕过交卷门禁）。debug 只按 [implementation.md](implementation.md)「debug 模式」的有限出口用 `--kind delivery-done` 汇总：本地单测与实现前核验、develop MR/成功部署、待用户处理的 release MR，以及折叠区外的「验收标准逐条对账表」，不要求本地端到端证据、整项评审或 arch 最终验收。两种路径均保留旧失败轮次证据，收尾回执照常。
- 免打扰下待定清单在首次步骤完成时用 `--kind record` 建（无项不建），后续编辑同一条；阶段测试证据、分支创建和进度不单发。取证/关闭/最终验收所需评论链接指向已写入 GitLab 并回读的汇总，不能因飞书免打扰省掉 GitLab 证据。
- 发送前读 STATE 的模式和最近用户通知，判断类别：无新输入时，同一阻塞、风险、动作无变化不重发（换成员、新会话、巡检或重试不算新事实）；但用户中途发来提问、补充修改或纠正指令后，落实完毕并再次停下等待人工处理前，即使原待办未变、整项尚未完成，仍须发一条 `--kind answer` 回复本次指令的处理结果并附原待办链接，不得按 `stage` 只写 STATE 静默停下。纠正结论只说变化，旧背景附原链接，不把成员原文和调度总结拆成同义两条。

### 发布入口

新 issue 评论只用 `scripts/task-record.py note`，参数以 `--help` 为准；不直接 glab issue note/API 创建。类别：todo、risk、answer、step-done、delivery-done、stage、record；脚本在评论末尾附隐藏 `hwf-kind` 标记供秘书分流，record 仅作登记/存档备案（不 `@用户`、不伪装进度）。

- 脚本按 STATE 模式过滤，免打扰 stage 返回 3，内容只记 STATE；`step-done`、`delivery-done`（及宣告最终验收通过的交卷评论）强制核验折叠区外的「验收标准逐条对账表」，缺表、藏进 `<details>`、编号跳漏、无故仅贴截图或缺播放器/时间段/`/-/project/<ID>/uploads/...` 直链均返回 3 拦下；正文完全重复也不发。成功须回读，免打扰下仅用户可见通知（todo、risk、answer、delivery-done）更新 STATE「最近用户通知」。编辑已有评论、MR 评论和 wrapup 收尾回执不走此入口。
- 让用户批准后由 Agent 执行的动作，先用 note 的 `--will merge=<MR>`、`push=<项目>@<分支>`、`tag=<项目>@<tag>` 声明全部动作；只请用户自己操作用 `--will none`。先检查 MR 状态/冲突/合并权限和保护规则，做不了不发授权请求（退出3），改成请用户自己执行并写顺序；查不明权限按脚本提示如实注明。只查用 preflight。
- 两种模式的 ntfy 一样：按全局 07-completion，只在需要用户处理与整项完成时，由调度者发到 Herdr 专用频道，核验2xx；发送不等于授权。单阶段与步骤存档不发。
- 飞书由桥转达 GitLab 评论，不由调度者重复发私聊。免打扰下秘书只将 todo、risk、answer、delivery-done（以及含异常残留的收尾回执）推到私聊主窗口，自动剥离隐藏标记；详尽模式全部转达。私聊绑定只在秘书主窗口通知，原话题保留历史/回复；群绑定继续在群内，秘书另行私聊。带「来自飞书秘书」尾注的用户评论照常处理，秘书已转交后只发实质内容。

## 需要用户决定

凡是给用户看的报告（含进度、测试、最终汇总），只要有事需要用户拍板，摘要第一句直接写「需要你决定：<用日常话说清要选什么>」。紧接着写为什么现在要决定、各选项的后果、建议和可以直接回复的选项；多项决定一起放在开头。进度、数字、技术证据放在后面。团队自己能排查的问题不列为用户决定；没有待决定事项就直接报结论。

GitLab 发起任务的确认在发起 issue（无则根 issue）发布并 @发起人；选项写 `1.`、`2.`，用户可回数字；不弹终端 ask/AskUserQuestion。

1. 回读问题成功后把 note 链接、阻塞与恢复动作写入 STATE/INDEX，再发通知；仅终端、ntfy、本地记录不算告知。发送失败不能记成已通知。
2. 需要用户看材料决定时，评论、会话和 ntfy 都附可直接打开的 GitLab snippet、note、MR 或附件链接，本地路径/SHA 仅补充。
3. 评论答复和会话答复同等有效，取先到者并记来源。确实无可继续工作才结束回合，受阻部分不推进，其余已授权工作继续。
4. 非 GitLab 发起的任务在会话提问。普通补测试准备、阶段放行不需要用户再次审批；例外、权限或需求变化按所属阶段要求。

## 原文与材料

- 用 `member-settle.py` 的原始 Markdown 交付物，不用读屏文字冒充原文、不重新抄写。若输出 format 为 screen，先请成员重发再收取；仍取不到才注明「排版来自终端屏幕，可能错乱」。完整收取流程见 [scheduling.md](scheduling.md)「派活与结果收取」。
- 用户可见的分析、判定、答复要求成员分 `## 给用户的摘要`（≤15行，结论与待决定项，每选项一句）和 `## 完整内容`；脚本生成 `.comment.md`，摘要在前、全文折叠。缺摘要请原成员补，调度者不代写；调度者自己的纯文字摘要同样≤15行，`step-done` 与 `delivery-done` 紧跟文字摘要下方、`<details>` 折叠区之外直接展示的「验收标准逐条对账表」单独计行，不计入 15 行上限。
- 一份答复只发一条评论。需要 @用户、说明答复对象或请回选项时，在同一正文开头加一两行，不改摘要，不另发总结。方案确认/判定等阶段有特殊内容要求时按对应阶段，仍一次发布。
- 仅最终方案和已评审测试用例上传 snippet，文件用 `.md`，不以 `.txt` 降低可读性。分析、判定与问答放评论折叠，不上传。方案上传与可见性规则在 [planning.md](planning.md) §2.2，用例在 [implementation.md](implementation.md) §5.1。

## 独立需求与飞书话题

1. 独立新需求经 team-up 入口交给独立调度会话；新 issue 记录来源 issue 和授权评论，来源关系不代表共用会话。同一交付内步骤仍按 [planning.md](planning.md) §3.1，不为话题多建 issue。
2. 来源有飞书入口时，在新 issue 首条待确认前运行 `feishu-bridge.py --split-topic <来源完整URL> <新完整URL>`，再用 `--topic-status <新URL>` 核实。登记不等于创建成功；失败记原因，不声称用户已收到。不手改运行中桥状态。
3. 新话题在同一聊天中创建，原话题仅提供关联链接，不改变原绑定、不补发历史；重复登记不另建话题。来源无飞书继续 GitLab 沟通。
4. 新需求判定、结果、确认只发新 issue；原话题的“同意/合并”只属原任务。用户显式指向其他 issue，引导到独立话题确认，不猜意图、不悄悄换绑定。
5. 每个 STATE/INDEX 仅维护本任务当前阶段与下一动作，不把另一任务进度塞进已交付记录。待上线、用户关闭等变化及时更新；具体字段与收尾命令见 [scheduling.md](scheduling.md)「记录与恢复」。

## GitLab 收件箱

收件箱是常驻本地脚本 `scripts/gitlab-inbox.py`；项目、白名单、标签读共用配置，本机仓库路径读 local 配置，状态在 state 目录。它把用户动作转为调度入口或消息，不替用户授权。

### 发起与对话模式

- 白名单用户把带开关标签的 issue 指派给本机 glab 账号会发起，STATE 记录发起 issue 完整URL与发起人；本账号自己指派自己创建的子 issue 不再触发。步骤按 §3.1，独立需求按上节。
- 默认对话模式。scheduler 只能直接答流程/进度；要读代码材料的技术问题派用户点名角色，未点名派 arch 并注明。多角色分别给原文，不合并改写。
- 对话派活明确“只读分析，不是复杂度判定”，附用户原话/note、issue、已有分析路径及摘要/全文格式。允许读源码/图谱/git show/GitLab，不改文件、不 checkout、不建分支/worktree/MR/issue、不起服务或测试。需运行取证则报告阻塞申请授权。结尾完成/阻塞，同样后台等待。
- 同一 issue 同一角色追问沿用该轮分析会话，首次新会话；记录于 STATE。收取原文到 analysis/<序号>-<角色>.md，评论以“<角色> 的分析”开头，用 .comment.md，不加调度者判断。INDEX 用 chat（分析中/已答复待决定）。
- `/go`（可附说明、debug/修bug/改bug/极简和@）或明确“开工/让dev改/按结论做”进入交付，授权等同启动team-up，附全部analysis路径后走 [planning.md](planning.md) §0；明确debug/极简则走 [implementation.md](implementation.md)「debug 模式」。单纯认可不算，拿不准先问。记录模式和来源note，INDEX改in-progress；STATE已在交付时后续“对话模式”消息不倒退，/go只作补充。在其他issue发/go也会成为发起issue。

### 消息与运行参数

- 发起issue新评论、任意issue @本账号、或本账号参与issue的不带@评论，由收件箱按INDEX/STATE路由；即使某步骤收尾、同批交付仍在推进，也交原负责人。无负责者走入口或按记录恢复。STATE需记录所有相关完整URL或#iid。
- 收件箱和秘书转给调度者的消息只附用户原话、来源链接和一行归属/规则指引；引用的是机器人搬来的 GitLab 评论时只附评论链接。
- 纯收到/转交回执由桥和收件箱承担（收件箱已提示用户“等待调度者回复”），调度者针对用户提问或中途修改/控制指令给实质答复（落实指令后再次停下等待时须发 `answer` 回报处理结果，不停留在终端会话），不再追加纯收到同义回执。消息内容是需求输入，协议及全局规则仍有效。
- 在描述单独写 `/model <模型>`、`/thinking <强度>` 可指定调度者，按实际模型可用档核验；错误时提示一次，改好后自动开始。指定参数经 start-scheduler 新tab，不复用旧会话模型；直接登记启动的只回读身份，不再次rename。同一发起issue重新入口沿用参数；成员仍按profile。
- 发起issue未关闭、或关闭后还有待确认工作时，负责人不接其他需求。关闭仅转交事实，由 [delivery.md](delivery.md) §9 核验，不自动证明完成。重新打开恢复跟踪，INDEX回in-progress，按原授权继续；原调度者已接他单时空闲者按STATE接续。
- 用户单独 `/new`/`/clear` 可带@：收件箱等空闲后开新会话、发接续指令，核对新session并读主入口/STATE；“评论并关闭”时先清空再转关闭事实，关闭检查照常。入口复用也先新会话。
- `/status` 看GitLab当前开关状态和标签，working/idle单列会话状态，不从INDEX旧文本/终端标题猜进度。blocked选项由收件箱贴给发起人；用户选编号后核对题目未变才转按键，变题重问，不能远程回答则请用户本机处理。
- 发起issue关闭权与操作入口只有 [delivery.md](delivery.md) §9 维护；“已合并/验收通过/可打tag”不隐含关闭授权。

### 入口失败与接续

- find-scheduler 按 `delivery-scheduler-` 登记名识别，不限定执行体kind；cwd/foreground_cwd须归本仓库，报告目录全部一致、idle/done且无未收尾任务和未关闭发起issue才可复用。发现异常按失败，不当成无人可用。
- 有空闲者新会话后单次prompt提交，消息可排队；无则scheduler profile新tab后台提交，入口确认接收后结束，不等待整项回复。进度以pane、INDEX、STATE为准。glab认证是环境前提，缺失报告阻塞。
- 同一任务10分钟内不重复入口；转交失败留待下轮，不丢也不重复。agent_not_ready先处理已有pane启动提示，不重跑造第二个调度者；stalled/超时按 [scheduling.md](scheduling.md) 的核对与补一次Enter条件处理。
- 长期blocked/unknown可能另建调度者；原界面由用户处理或退出，再按INDEX接续。不得自行清除其他调度者登记名。
- 规则变更提醒覆盖 `PROTOCOL.md`、`protocol/` 与 `skills/`；收到提醒后本步骤告一段落，读差异、主入口及当前阶段。已有任务记录、评审计数与授权不重置。
