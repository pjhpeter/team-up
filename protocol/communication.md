# 沟通、通知与收件箱

用户需要看到的是结果和待办，不是每次派活的流水。调度者统一对外发布，区分阶段结果与完整交付；事实和证据留在任务记录，需要用户处理时再明确通知。

## 沟通边界

- 成员只向调度者交付和提问，不直接向用户发消息、弹通知、要求操作，不在 GitLab issue/MR 评论或改状态（仅 test 可用 `scripts/upload-media.py` 静默上传本轮录屏/截图附件换取链接交调度者汇总），不发送 ntfy。调度者收取后统一发布、回读；成员报告阻塞不替代调度者通知。
- 调度者先查能否由已有授权或成员解决阻塞；判断前先核对已签发方案与当前真实环境，不把草稿假设或单次可恢复的资源/环境故障当成永久硬阻塞停下；可继续的授权工作照常推进，严禁在「待用户事项：无」时仅于终端或本地 STATE 写「暂停/收口」就结束回合。确需暂停或等用户决策时，必须先发 `--kind todo`（写清停在哪、原因、不受阻可继续项与恢复条件）、贴 `状态:等你处理`、更新 STATE「待用户事项」并发 ntfy，不以“成员问了”直接转成用户待办。用户启动交付流程（含 `/go`、debug/极简模式）即包含以下常规执行动作，团队直接按对应章节自理，**严禁发 `todo` 向用户请示或要求二次确认**：
  1. 创建、复用与推送 `release-<根编号>` 汇总分支、开发分支及冲突集成分支；
  2. 创建并合并指向 `develop`（`branches.test`）的测试分支 MR，以及冒烟通过后合入 `release-<根编号>`；
  3. 本地验收时在本 issue 独立 worktree 启动专属 Web 服务或开发版 Electron（受固定端口如 `3001` 约束时，核实端口空闲后直接启动、测完清理，不为“能否启动本地 Electron/Web”或“没有签名安装包”请示用户）；
  4. 可通过 `glab`、`git`、分支/MR/流水线状态或项目配置自行核实的客观事实（如评论已说明某分支/提交已合并或部署，直接查证，不再发评论请用户或同事确认）；
  5. 现有测试环境客观无法构造的隔离环境、独立登录网关/资产服务、Runner 标签改造或极低概率历史旧端场景（按 [PROTOCOL.md](../PROTOCOL.md) 红线 6 与门槛 3 直接以定向单测、代码审查与剩余风险说明闭环，不向用户索要特殊环境或反复请示豁免）。
- 阶段通过不等于交付完成。详尽模式的阶段评论首句为「本轮<阶段>通过，整项需求尚未完成」，列剩余步骤、下一动作，再附原文与测试录屏/截图证据；明确本地、测试环境、生产环境和版本，本地 develop 模式不是部署成功。
- 尚待上线写清「尚未上线」，不提示可以关闭；最终验收、关闭请求及实际关闭事件按 [PROTOCOL.md](../PROTOCOL.md) 红线 1 与门槛 3–4 先核对证据，不把用户认可理解成放弃剩余工作。

## 通知模式

默认免打扰；详尽模式额外发布单阶段结果，但不降低任何证据要求。

| 时机 | 免打扰（GitLab / 飞书私聊） | 详尽（GitLab / 飞书私聊） |
|---|---|---|
| 新增/实质变化的用户待办、数据安全风险（`todo`/`risk`） | 写 GitLab 并立即推飞书私聊＋ntfy | 相同 |
| 用户问题或中途修改指令的实质答复、对话模式结论、`/status`（`answer`） | 写 GitLab 并立即推飞书私聊 | 相同 |
| 整项完成/最终验收请求（`delivery-done`） | 写 GitLab 一条汇总并立即推飞书私聊＋ntfy | 相同 |
| 每个步骤或子 issue 完成（`step-done`） | 只写 GitLab 一条汇总备查，**不推飞书私聊** | 写 GitLab 并推飞书私聊 |
| 已确认方案/已评审用例备案、待定清单、登记池（`record`）及正常收尾回执 | 只写 GitLab 存档备查，**不推飞书私聊** | 写 GitLab 并推飞书私聊 |
| 评审、本地测试、冒烟的单阶段结果（`stage`） | 只记 STATE，不发评论 | 发阶段评论（注明整项未完成）并推飞书 |
| 开工、切模式、清空上下文等纯命令回执 | 收件箱写 GitLab，**免打扰不推飞书私聊** | 推飞书私聊；调度者不重复确认 |

- STATE 顶部「通知模式」记录模式和来源；没写即免打扰。用户单独发送 `/免打扰`/`/quiet` 或 `/详尽`/`/verbose`，或在会话直接要求，即从收到起切换；收件箱回确认后调度者只改 STATE，不再确认，不补发或撤回历史评论。
- 常规多步骤交付的步骤汇总用 `--kind step-done` 写根 issue（不 `@用户`），一次附评审、测试分支 MR/部署、release MR/SHA、待定项条数，以及折叠区**之外**的「验收标准逐条对账表」（每行含结果、播放器 `markdown`、起止时间段与 `/-/project/<数字ID>/uploads/...` 直链或免录原因）；整项汇总在独立真机验收与 `release-check` 通过后统一用 `--kind delivery-done` 发布（即使仍需等待用户点击合并或跨团队前置上线，也用 `delivery-done` 一次写清前置顺序与对账表，不用 `todo` 绕过交卷门禁）。debug 同样用 `--kind delivery-done` 汇总：先红后绿单测、develop MR/成功部署、待用户处理的 release MR，以及折叠区外的「验收标准逐条对账表」，不要求整项代码评审。两种路径均保留旧失败轮次证据，收尾回执照常。
- 免打扰下待定清单在首次步骤完成时用 `--kind record` 建（无项不建），后续编辑同一条；阶段测试证据、分支创建和进度不单发。取证/关闭/最终验收所需评论链接指向已写入 GitLab 并回读的汇总，不能因飞书免打扰省掉 GitLab 证据。
- 发送前读 STATE 的模式和最近用户通知，判断类别：无新输入时，同一阻塞、风险、动作无变化不重发（换成员、新会话、巡检或重试不算新事实）；但用户中途发来提问、补充修改或纠正指令后，落实完毕并再次停下等待人工处理前，即使原待办未变、整项尚未完成，仍须发一条 `--kind answer` 回复本次指令的处理结果并附原待办链接，不得按 `stage` 只写 STATE 静默停下。免打扰模式下 `--kind answer` 仅用于回复原 issue 未答复的新用户留言或对话模式首次分析结论；回复过一次后，后续未完成阶段进展只更新 STATE，**严禁在无新用户留言时继续用 `--kind answer` 播报中间进度**（需拍板/操作用 `todo`，新风险或流程违规用 `risk`，整步留档用 `step-done`，整项交卷用 `delivery-done`）。纠正结论只说变化，旧背景附原链接，不把成员原文和调度总结拆成同义两条。

### 发布入口

新 issue 评论只用 `scripts/task-record.py note`，参数以 `--help` 为准；不直接 glab issue note/API 创建。类别：todo、risk、answer、step-done、delivery-done、stage、record；脚本在评论末尾附隐藏 `hwf-kind` 标记供秘书分流，record 仅作登记/存档备案（不 `@用户`、不伪装进度）。

- 脚本按 STATE 模式过滤，免打扰下 `stage` 直接返回 3（只记 STATE），`answer` 同时核对原 issue 水位，若上一条面向用户的回复之后无新用户留言同样返回 3 拦下（防止拿 `answer` 变相播报中间进度）；`step-done`、`delivery-done`（及宣告最终验收通过的交卷评论）强制核验折叠区外的「验收标准逐条对账表」，缺表、藏进 `<details>`、编号跳漏、无故仅贴截图或缺播放器/时间段/`/-/project/<ID>/uploads/...` 直链均返回 3 拦下；`delivery-done` 同时执行「代码作者 ≠ 代码评审者 ≠ 真机验收者」独立性硬校验，缺独立角色或窗格/会话重合均返回 3 拦下；正文完全重复也不发。用 `state-set` 将任务切为等待用户或 `待上线` 时，脚本同步核对原 issue 是否存在晚于最近实质回复的未答用户留言，若有则返回 3 提示先补 `answer`。成功须回读，免打扰下仅用户可见通知（todo、risk、answer、delivery-done）更新 STATE「最近用户通知」。编辑已有评论、MR 评论和 wrapup 收尾回执不走此入口。
- 让用户批准后由 Agent 执行的动作，先用 note 的 `--will merge=<MR>`、`push=<项目>@<分支>`、`tag=<项目>@<tag>` 声明全部动作；只请用户自己操作用 `--will none`。先检查 MR 状态/冲突/合并权限和保护规则，做不了不发授权请求（退出3），改成请用户自己执行并写顺序；查不明权限按脚本提示如实注明。只查用 preflight。
- 两种模式的 ntfy 一样：按全局 07-completion，只在需要用户处理与整项完成时，由调度者发到 Herdr 专用频道，核验2xx；发送不等于授权。单阶段与步骤存档不发。
- 飞书由桥转达 GitLab 评论，不由调度者重复发私聊。免打扰下秘书只将 todo、risk、answer、delivery-done（以及含异常残留的收尾回执）推到私聊主窗口，自动剥离隐藏标记；详尽模式全部转达。私聊绑定只在秘书主窗口通知，原话题保留历史/回复；群绑定继续在群内，秘书另行私聊。带「来自飞书秘书」尾注的用户评论照常处理，秘书已转交后只发实质内容。

## 需要用户决定

凡是给用户看的报告（含进度、测试、最终汇总），只要有事需要用户拍板，摘要第一句直接写「需要你决定：<用日常话说清要选什么>」。紧接着用 2–3 句大白话讲清卡在哪、不选会怎样、各选项的后果、建议和可以直接回复的选项；多项决定一起放在开头。进度、数字、技术证据放在后面，**禁止**用内部验收编号（如 `E13`、`B05`、`§28`）、类名或行话当主语。团队自己能排查的问题不列为用户决定；没有待决定事项就直接报结论。

**提问门槛（只问真有业务取舍或必须人工动手的事项）**：发 `todo` 请用户拍板前，必须满足「确实影响主流程或核心数据安全，且存在至少两个有实际代价的业务/产品选项（或确需用户本人操作，如生产 SQL、合并 `main`、真人验证码）」。以下情形**严禁**做成用户待办反复追问，团队直接在现有条件下处理或单测/审查兜底并披露剩余风险即可：
- 现有测试环境客观不存在的隔离环境、独立登录网关、独立资产服务、Runner 标签/权限改造或历史未归档包对比；
- 极低概率的历史冷门旧端角落，或可在工程内按保守默认/单测兜底自行判断的低概率边界；
- 用户已经明确表态「不提供特殊环境」「按现有环境做」「接受风险」的同类事项，不得换个说法再次追问。

GitLab 发起任务的确认在发起 issue（无则根 issue）发布并 @发起人；选项写 `1.`、`2.`，用户可回数字；不弹终端 ask/AskUserQuestion。

1. 回读问题成功后把 note 链接、阻塞与恢复动作写入 STATE/INDEX，再发通知；仅终端、ntfy、本地记录不算告知。发送失败不能记成已通知。
2. 需要用户看材料决定时，评论、会话和 ntfy 都附可直接打开的 GitLab snippet、note、MR 或附件链接，本地路径/SHA 仅补充。
3. 评论答复和会话答复同等有效，取先到者并记来源。确实无可继续工作才结束回合，受阻部分不推进，其余已授权工作继续。
4. 非 GitLab 发起的任务在会话提问。普通补测试准备、阶段放行不需要用户再次审批；例外、权限或需求变化按所属阶段要求。
5. **人脑审核护栏（合并提问与限流）**：同一任务里有多个待决项时，先做完不受阻工作再打包成一条清单一次问清（多项拍板优先附可勾选并一键复制指令的交互 HTML 决策页），不挤牙膏式分条打断；非紧急复盘/观察走固定时间窗；秘书巡检发现同时待用户拍板或待上线的需求达到 3 个及以上时会在顶部提醒先集中清完存量再开新任务。本护栏只控打断与并发，不越过对话模式、开工前/交付后本人验收确认、手动关单与 `main` 禁止自动合并这几条人工红线。

## 原文与材料

- 用 `member-settle.py` 的原始 Markdown 交付物，不用读屏文字冒充原文、不重新抄写。若输出 format 为 screen，先请成员重发再收取；仍取不到才注明「排版来自终端屏幕，可能错乱」。
- 用户可见的分析、判定、答复要求成员分 `## 给用户的摘要`（≤15行，结论与待决定项，每选项一句）和 `## 完整内容`；脚本生成 `.comment.md`，摘要在前、全文折叠。缺摘要请原成员补，调度者不代写；调度者自己的纯文字摘要同样≤15行，`step-done` 与 `delivery-done` 紧跟文字摘要下方、`<details>` 折叠区之外直接展示的「验收标准逐条对账表」单独计行，不计入 15 行上限。
- 一份答复只发一条评论。需要 @用户、说明答复对象或请回选项时，在同一正文开头加一两行，不改摘要，不另发总结。
- 仅在调度者按需启用了正式方案或独立测试用例时用 `upload-snippet.py` 上传 `.md` snippet。分析、验收卡与问答放评论折叠，不上传。

## 独立需求与飞书话题

1. 独立新需求经 team-up 入口交给独立调度会话；新 issue 记录来源 issue 和授权评论，来源关系不代表共用会话。同一交付内关联工作不为了建话题而多建 issue。
2. 来源有飞书入口时，在新 issue 首条待确认前运行 `feishu-bridge.py --split-topic <来源完整URL> <新完整URL>`，再用 `--topic-status <新URL>` 核实。登记不等于创建成功；失败记原因，不声称用户已收到。不手改运行中桥状态。
3. 新话题在同一聊天中创建，原话题仅提供关联链接，不改变原绑定、不补发历史；重复登记不另建话题。来源无飞书继续 GitLab 沟通。
4. 新需求判定、结果、确认只发新 issue；原话题的“同意/合并”只属原任务。用户显式指向其他 issue，引导到独立话题确认，不猜意图、不悄悄换绑定。
5. 每个 STATE/INDEX 仅维护本任务当前阶段与下一动作，不把另一任务进度塞进已交付记录。待上线、用户关闭等变化及时更新；收尾命令见 [PROTOCOL.md](../PROTOCOL.md) 第四节。

## GitLab 收件箱

收件箱是常驻本地脚本 `scripts/gitlab-inbox.py`；默认动态覆盖本机机器人可访问的全部非归档 GitLab 项目（`gitlab-inbox.config.json` 省略或清空 `projects` 即全量动态发现；本机仓库路径在 `gitlab-inbox.local.json` 维护，首次需要启动调度者而本机尚无仓库时自动 `git clone` 到 `~/code/<repo>` 并落盘）。它把用户动作转为调度入口或消息，不替用户授权。

### 发起与对话模式

- 任意人把任意非归档项目的 issue 指派给本机机器人账号（`pjhagent`），或白名单用户打开关标签并指派给机器人，都会登记并启动只读**对话模式**（`CHAT`，不要求提前打 `herdr-auto`）；本账号自己指派自己创建的子 issue 不再触发。所有涉及改代码、开工、建分支或控制会话的操作（`/go`、`DEBUG_WORDS`、自然语言开工、`/new`、`/clear`、`/quiet`、`/verbose`、终端选项回复）严格只认白名单用户（`allowed_users`）。
- 任意非归档项目中，指派给白名单本人（`pengjh`）或评论中 `@pengjh`（未同时指派/提及机器人）的议题，收件箱通过本人只读凭据登记为 `standby` 并推送到飞书秘书私聊提醒，等待本人指示，不自动克隆仓库、不改本人待办状态、不启动调度者；用户后续在 issue 或飞书 `@机器人` 接手并成功转交调度者后，自动解除 `standby`（保持原通知水位不重弹提醒），纳入活跃巡检与空转告警。
- 默认对话模式。scheduler 只能直接答流程/进度；要读代码材料的技术问题派用户点名角色，未点名派 arch 并注明。多角色分别给原文，不合并改写。
- 对话派活明确“只读分析，不是复杂度判定”，附用户原话/note、issue、已有分析路径及摘要/全文格式。允许读源码/图谱/git show/GitLab，不改文件、不 checkout、不建分支/worktree/MR/issue、不起服务或测试。需运行取证则报告阻塞申请授权。结尾完成/阻塞，同样后台等待。
- 同一 issue 同一角色追问沿用该轮分析会话，首次新会话；记录于 STATE。收取原文到 analysis/<序号>-<角色>.md，评论以“<角色> 的分析”开头，用 .comment.md，不加调度者判断。INDEX 用 chat（分析中/已答复待决定）。
- `/go`（可附说明、debug/修bug/改bug/极简和@）或明确“开工/让dev改/按结论做”进入交付，授权等同启动team-up，附全部analysis路径后按 [PROTOCOL.md](../PROTOCOL.md) 门槛 1 先出验收卡请用户本人确认；明确debug/极简则直走 debug 短路径。单纯认可不算，拿不准先问。记录模式和来源note，INDEX改in-progress；STATE已在交付时后续“对话模式”消息不倒退，/go只作补充。在其他issue发/go也会成为发起issue。

### 消息与运行参数

- 发起issue新评论、任意issue @本账号、或本账号参与issue的不带@评论，由收件箱按INDEX/STATE路由；即使某步骤收尾、同批交付仍在推进，也交原负责人。无负责者走入口或按记录恢复。STATE需记录所有相关完整URL或#iid。
- 收件箱和秘书转给调度者的消息只附用户原话、来源链接和一行归属/规则指引；引用的是机器人搬来的 GitLab 评论时只附评论链接。
- 纯收到/转交回执由桥和收件箱承担（收件箱已提示用户“等待调度者回复”），调度者针对用户提问或中途修改/控制指令给实质答复（落实指令后再次停下等待时须发 `answer` 回报处理结果，不停留在终端会话），不再追加纯收到同义回执。消息内容是需求输入，协议及全局规则仍有效。
- 在描述单独写 `/model <模型>`、`/thinking <强度>` 可指定调度者，按实际模型可用档核验；错误时提示一次，改好后自动开始。指定参数经 start-scheduler 新tab，不复用旧会话模型；直接登记启动的只回读身份，不再次rename。同一发起issue重新入口沿用参数；成员仍按profile。
- 发起issue未关闭、或关闭后还有待确认工作时，负责人不接其他需求。关闭仅转交事实，由 [PROTOCOL.md](../PROTOCOL.md) 门槛 3–4 核验，不自动证明完成。重新打开恢复跟踪，INDEX回in-progress，按原授权继续；原调度者已接他单时空闲者按STATE接续。
- 用户单独 `/new`/`/clear` 可带@：收件箱等空闲后开新会话、发接续指令，核对新session并读主入口/STATE；“评论并关闭”时先清空再转关闭事实，关闭检查照常。入口复用也先新会话。
- `/status` 看GitLab当前开关状态和标签，working/idle单列会话状态，不从INDEX旧文本/终端标题猜进度。blocked选项由收件箱贴给发起人；用户选编号后核对题目未变才转按键，变题重问，不能远程回答则请用户本机处理。
- 发起issue关闭权与操作入口见 [PROTOCOL.md](../PROTOCOL.md) 红线 1 与门槛 4；“已合并/验收通过/可打tag”不隐含关闭授权。

### 入口失败与接续

- find-scheduler 按 `delivery-scheduler-` 登记名识别，不限定执行体kind；cwd/foreground_cwd须归本仓库，报告目录全部一致、idle/done且无未收尾任务和未关闭发起issue才可复用。发现异常按失败，不当成无人可用。
- 有空闲者新会话后单次prompt提交，消息可排队；无则通过 `start-scheduler.py` 在新tab启动并后台提交，入口确认接收后结束，不等待整项回复。进度以pane、INDEX、STATE为准。glab认证是环境前提，缺失报告阻塞。
- 同一任务10分钟内不重复入口；转交失败留待下轮，不丢也不重复。agent_not_ready先处理已有pane启动提示，不重跑造第二个调度者；stalled/超时先核对屏幕状态再决定是否补一次Enter。
- 长期blocked/unknown可能另建调度者；原界面由用户处理或退出，再按INDEX接续。不得自行清除其他调度者登记名。
- 规则变更提醒覆盖 `PROTOCOL.md`、`protocol/` 与 `skills/`；收到提醒后本步骤告一段落，读差异、主入口及当前阶段。已有任务记录、评审计数与授权不重置。
