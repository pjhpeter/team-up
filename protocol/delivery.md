# 发布汇总、验收与收尾

通过测试的代码必须能对应到待上线版本，关单也必须有证据。本主题把汇总分支、测试环境冒烟、最终验收与收尾串起来，避免「issue 关了，代码和进程却没交代清楚」。

第一次派 dev 前读「根 issue 汇总分支」和「上线清单」；完成测试后读 §9，根交付结束前读 §9.1。评审与每轮测试见 `review-testing.md`；通知、收件箱消息转交见 `communication.md`，关闭授权以本文件 §9 为准；成员状态、pane 管理见 `scheduling.md`；目录与资源清理判据见 `worktrees.md`。

## 根 issue 汇总分支

每个根 issue 有且只有一个远端汇总分支 `release-<根 issue 编号>`，它是本需求已验收、可上线代码的唯一出处。根是交付最上层 issue：方案路径的 spec、直达路径唯一 issue、或 GitLab 收件箱发起 issue；步骤/子 issue 全部汇入根分支。

### 创建与开发基线

- scheduler 第一次派 dev 前基于 `origin/main` 创建：`git push origin origin/main:refs/heads/release-<编号>`，用 `git ls-remote origin release-<编号>` 回读，根 issue 评论与 STATE 记录分支和基线 SHA。已存在则复用，不重建、改名或 force push。
- 同时按 `planning.md`「issue 数量与进度标签」在根描述顶部建「进度」「上线清单」维护区，不另建上线清单 issue。
- 根 issue 及步骤/子 issue 的开发分支从汇总分支最新提交切出，命名 `feat|fix/issue-<本 issue 编号>-<简述>`，不得从 develop 切出。缺依赖时 dev 停下报 scheduler，由 arch 判断纳入依赖 issue 还是请用户确认（debug 直接请用户确认，不派 arch），不私自整段合 develop。
- 用户指定其他基线/目标（如 `release-x.y.z`）时，替代默认汇总分支，其余步骤不变，develop 冒烟仍必做。

### 合并顺序与版本一致性

正常流程一般通过 `review-testing.md` §7（含 arch 放行）和 §8 本地验收后执行以下顺序；满足 `review-testing.md` §8「单分支低风险直达合并冒烟」条件时，通过 §7 后直接执行第 1 步，在 `smoke` 一次性完成已评审用例验收与冒烟。debug 的独立顺序与有限出口只按 `implementation.md`「debug 模式」：开发及实现前核验后可合 develop、等待部署并验收，通过后只创建 release MR，不要求 §7/arch 放行，不合 release/main、不关闭 issue，也不进入汇总完整性评审和 §9.1。

1. scheduler 提开发分支 → develop 的 MR，可立即合并；等对应流水线部署作业成功，按 §9「测试环境冒烟」验证。
2. 冒烟通过，再提同一开发分支 → 汇总分支的 MR，无需逐次确认。回读目标分支、源 SHA、diff，确认源 SHA 与 develop 合入并冒烟的相同，diff 只含本 issue 改动，再立即合并并回读汇总分支已包含该 SHA。
3. 冒烟不通过或冒烟后又改功能代码，按 `review-testing.md` §8「测试失败后的回改」执行：回 dev 单趟完成改前红证、修复与改后绿证 → code-review 增量核验（最多 2 轮）→ 合入 develop 部署并重新冒烟（未涉及本地独有环境或桌面原生差异时，无需退回重起本地服务）。

解冲突可使 SHA 不同，但本需求代码必须对应：develop、汇总分支、main 解冲突的新提交，逐个核对本需求改过的文件与冒烟版本。仅本需求外的差异允许；本需求代码被改写时，正常流程在新版本本地重跑本次浏览器测试项，碰到功能逻辑再合 develop 重新冒烟；debug 则回干净开发分支按 `implementation.md`「回改打包」单趟完成红绿留证与核验，再部署 develop 复测，不本地跑浏览器验收。STATE 与完成评论记录冒烟版本、目标版本、本需求文件是否一致、不一致如何验证。develop 只作测试环境，不是可上线依据；禁止把 develop 合入汇总分支。

### 测试分支冲突与指定目标

直接提 MR 到测试分支会冲突、分叉大或带入无关改动，且未获准把 develop/stage 合入原开发分支时，由 dev 从最新测试分支建独立集成分支及 worktree，只集成本需求提交，解冲突并定向验证。正常流程要求这些提交已审、集成增量经 code-review 核验（**仅核冲突消解是否保留已审本需求行为与必要回归，不对已审逻辑重开挑刺，最多 2 轮**；第 2 轮仍未过由 arch 一次定死改法并仅核点名项落实，未消除则报阻塞交用户决定）；debug 按 `implementation.md` 的部署后验收执行，不增设整项代码评审。原开发和汇总分支保持干净；集成分支仅用于测试环境，不得合 release/main。冒烟后仍从原开发分支向目标提 MR，并按上一节核对已测代码；集成中发现必须回干净开发分支修改本需求功能逻辑时，按 `review-testing.md` §8「测试失败后的回改」走单趟闭环与增量核验（最多 2 轮，不重开 §7 首审），再更新集成副本、重跑受影响验证并部署冒烟，不只改集成副本。

用户指定其他基线/目标时，一律从最新测试分支建 `<开发分支>-develop` 集成分支，只 cherry-pick 本需求提交，按本段对应模式核验后合 develop、部署、冒烟；原开发分支仍按对应模式的出口交付，debug 仅创建目标 MR、不合并。分叉大、冲突多、目标无流水线都不能免掉冒烟。

仅成员确认有授权内无法解决的业务取舍、缺失依赖、范围扩张，才按 `communication.md`「需要用户决定」提具体问题。不能因禁止未经授权合 develop 就停掉整个任务；「继续完成剩余步骤」只恢复原范围，不授权合 develop 到开发或汇总分支。

### 汇总登记与完整性核对

- 被替代、作废、仅 develop 实验等不上线情况，必须写根 issue 并获用户确认，不能默认只进 develop。
- 子 issue 关闭前代码已在汇总分支或登记不上线。完成评论记录 develop MR、冒烟结果、汇总 MR/SHA，并更新「上线清单」。步骤不是 issue：根评论标题用「步骤 <序号> 完成：<名称>」，记录相同内容，再把汇总后的提交写进步骤 JSON、用 `task-record.py progress --steps-file` 重跑，由脚本核对后打勾。
- 全部步骤完成、子 issue 关闭或登记不上线后，scheduler 先运行：

  ```bash
  python3 ~/.hwf/scripts/task-record.py release-check --repo <仓库路径> --release release-<根编号> \
    --base origin/main --develop origin/<测试分支> --commit <各步骤源SHA>...
  ```

- **单步同树直通**：单仓库单步骤交付中，若 `release-check` 退出码 `0` 且输出 `same_tree_as_single_commit: yes`（即 `origin/release-<根编号>` 代码树与 `§6/§7` 已跑过相关 lint、type-check、测试并经评审放行的源提交完全一致，`origin/main..origin/release-<根编号>` 无额外提交，且本需求改动文件与 `develop` 完全一致），scheduler 直接把 `release-check` 输出与 `§6/§7` 验证记录写入根评论与 `STATE.md`，无需另派 `precheck` 与 `code-review` 重跑同一提交。
- **多步汇总、解冲突或存在差异**：多步骤/多分支汇总、汇总过程做过冲突处理、`same_tree_as_single_commit: no`，或 `release-check` 退出码 `3` 时，scheduler 派 precheck 取证、code-review 逐项核对：
  1. 完成评论源 SHA 都是汇总分支祖先（`git merge-base --is-ancestor`）。
  2. 各 issue 改过的每个文件与 develop 内容一致；差异逐个解释，其他需求差异可接受，本需求缺失或夹带未审改动不行。
  3. `git log origin/main..origin/release-<根编号>` 无不属于本需求的提交。
  4. 在汇总分支跑相关 lint、type-check 与本需求测试。
- 通过/缺失清单、核对 SHA、证据写根评论；有缺失先单趟补齐再核对（最多 2 轮，仍未通过即报阻塞交用户决定），未通过不得建 main MR、不得标交付完成。
- 查看本需求能上线什么，以根「上线清单」及上述 git log 为准，不另建表格或 issue 替代。

## 9. 调度者核验、关闭与集中收尾

### 测试环境冒烟

执行「合并顺序与版本一致性」的 develop 部署阶段时：

- 地址取 `docs/agents/herdr-project.yaml` 的 `smoke`，默认只测 `default` 不为 `false` 的地址。`default: false` 仅需求涉及或用户要求时测；未测在完成汇报写「<名称>未验（默认不验）」，不算缺项。列表为空先问用户，不猜地址。
- test 在测试环境逐条走本次验收点，每条一张截图、一句结论，确认应用可加载；造数、浏览器、服务和截图交付执行 `review-testing.md` §8。debug 按其「debug：部署后验收」，不启动独立本地验收服务，不关闭远端服务；正常流程不因本例外改变。只看首页或 HTTP 200 不算，不能用本地/同版本浏览器结果替代。
- 只有对应 develop 流水线部署成功后，在 `smoke` 地址逐点验证才叫冒烟；本机单测、本地 develop 页面、合指定目标后本地复核只能写「合入后本地复核」。流水线未成功不得声称冒烟通过。
- 测试环境不可达、缺生产数据等无法验证点逐条写原因，在完成汇报列未验证。整个需求无法合 develop 或部署时，按 `communication.md`「需要用户决定」请用户决定；正常流程只有对本需求明确同意才跳过，在完成汇报和 arch 包写「未经 develop 冒烟（用户同意：<note 链接>）」。debug 缺测试分支、地址、部署或可用测试客户端即阻塞，不自行转本地、跳过或创建最终交付 MR；改变约定出口须用户另行明确授权。

### 交付证据核验

scheduler 回收实际输出，核对：

- 每条验收有运行证据，测试 HEAD 对应交付 HEAD，严重问题已消除。
- `implementation.md` §6 的单元测试先行证据和用例更正审批（若有）齐全。
- UI 走查结论和截图齐全，浏览器截图满足 `review-testing.md` §8 截图交付门禁。
- 正常流程根需求已评审用例 snippet 已上传、回填 issue、可访问，测试执行版本与 snippet SHA 一致；步骤/子 issue 引用同一 snippet，不重复上传。debug 不要求 snippet，核对 issue 验收条目、部署版本和逐条证据。
- 测试服务、后台进程已按 `review-testing.md` §8 清理，所有使用端口回读空闲。本地验收轮次发现复用他人或先前 issue 服务，本轮不放行，须新启动独立服务重跑；发现残留先清理，不得报完成或关单。直接测已部署环境的轮次（单分支低风险直达合并冒烟、测试环境冒烟、debug）仅清理本任务本机浏览器、测试客户端和辅助进程，回读使用的本地端口，不启动本地验收服务、不关闭远端服务。

开发自报、成员 idle、命令无报错、未执行用例不能替代证据。

### 完成评论与关闭前核对

完成评论、最终验收请求、关闭操作、成员/worktree 收尾前，都回读：评审/测试版本，测试分支合并与部署，develop MR、成功部署作业、测试环境逐条截图链接（或用户同意跳过的 note），release 汇总及完整性核对，arch 最终验收，用户要求的交付目标。debug 仅核对 `implementation.md`「debug 模式」明确授权出口。用户验收回复和关闭事件不能补证。

- 收到「验收通过、关闭 issue」但仍有缺项：原 issue 首句写「尚未交付完成，还差<具体步骤>」，提供「继续完成」或「取消这些剩余步骤、不再交付」。保持 open，INDEX 写 `blocked（等用户确认剩余工作）`，保留成员/worktree；明确取消才按取消收尾，不能算交付通过。
- 已关 issue 但缺证且未明确取消：不自动重开、不标已交付，说明缺项，请用户重开继续或明确取消，INDEX 保持 blocked。每轮测试服务仍关闭，成员/worktree 留到用户决定；关闭事件不触发破坏性清理。
- 全部完成或用户明确取消才收尾；取消记录未交付项与用户原话。发起 issue 按本节「发起 issue 的关闭授权」处理；验收回复不替代 main 合并授权。

冒烟通过且代码已汇总后，原 issue 中文完成评论写结果、HEAD、develop MR、冒烟结果、汇总 MR/SHA、证据、本步新增待定项数量；更新上线清单，用 `task-record.py progress --steps-file` 刷新进度（勾选由脚本核对），再关子 issue 并回读 `state=closed`。子 issue 关闭/步骤勾选仅表示进入可上线分支，不代表部署。发起/根 issue 完成评论必须等 §9.1 通过。

失败或缺证项保持未完成，列阻塞与恢复动作；标签按 `planning.md`「issue 数量与进度标签」，需用户处理时 `状态:等你处理`。

### 上线与根 issue 关闭

全部步骤完成后，先「汇总登记与完整性核对」，再 §9.1，均通过才创建汇总分支 → main 的 MR（不合并）并收尾。MR 标题与描述**严禁**出现 `fix: #编号`、`fixes #编号`、`closes #编号`、`resolves #编号` 等 GitLab 自动关单语法（`fix:` 后不得直接跟 `#编号`，统一写 `fix: <简述>（关联 #<编号>）`）；创建后必须回读冲突、流水线状态及 `merge_requests/<iid>/closes_issues` 确认为空，完成汇报首行给 MR 链接。MR 描述的「冒烟核对」必须写 develop 冒烟版本、MR 源版本、本需求文件是否一致；main 解冲突新提交须列本需求修改文件、新版本重跑测试与结果，缺这些不得提 MR。用户指定其他汇入目标同样适用。

**main 的 MR 永不自动合并、永不夹带自动关单，只有用户明确授权才可合并**；遵守全局 main MR 禁止自动合并铁律。main 合入后若有 develop 没有的提交，再把 main 合回 develop。

根 issue 关闭表示已上线：全部步骤/子 issue、整体验收、完整性核对通过，main MR 经用户授权合并后，先评论合并 MR/SHA 再关闭。此前保持 open、`状态:待上线`。整体作废经用户确认写原因关闭。收件箱发起 issue 另须满足「发起 issue 的关闭授权」。

main MR 创建后，完成汇报逐条列根待定清单未处理项，各一句并建议做/不做，请用户挑选。点名项在本交付派成员处理、复核、测试后标已处理；未点名保持原样，不开 issue、不排期、不影响收尾，不谎称已处理。

### 发起 issue 的关闭授权

用户必须在评论或会话明确说「帮我关闭 / 关掉这个 issue」，scheduler 才能关闭或派成员关闭发起 issue；即使它就是 spec 或直达路径唯一 issue 也一样。「验收通过」「已合并」「可以打 tag」都不算关闭要求。

- 明确要求后，也只能通过下节 `wrapup.py --close-request <用户评论链接>` 在全部收尾通过后关闭，禁止用 glab/API 直接关闭。只有会话授权而无评论链接时，先请用户在该 issue 下留一句关闭要求，再执行。
- 完成「完成评论与关闭前核对」及 §9.1 最终验收后，才在发起 issue 写交付结论并 @发起人；仍待上线则列未合并目标 MR，不提示可以关闭。满足已授权交付出口后，才由收尾脚本把 INDEX 写为 `done（待用户处理上线或关闭）`。
- 用户继续评论就接续返工或补充；收到关闭请求或事件仍先核对交付证据，不能以验收通过豁免剩余步骤。交付中创建的其他 issue 按 §9 核验后关闭。
- 发起 issue 未关闭，或关闭后仍有待确认的未完成工作，负责 scheduler 不接其他需求。收件箱转交关闭事实不代表完成；缺项保持 blocked 等用户确认，完成收尾后才由脚本写 closed/cancelled。
- 用户重开时恢复跟踪，把 INDEX 改回 in-progress，按原授权范围继续；原 scheduler 已接其他任务时由空闲 scheduler 按 STATE 接续。收件箱转交和清空会话机制见 `communication.md`「GitLab 收件箱」，换会话不豁免本节核对。

### 集中收尾与回执

通过关闭前核对、全部交付完成或用户明确取消后，scheduler 主动收尾，不等提醒。阶段测试结束、阻塞等待、单独关闭事件都不是交付结束。

关闭 issue 前、INDEX 改收尾状态前、成员 pane 关闭前，scheduler 必须亲自对名下每个 worktree 执行 `python3 ~/.hwf/scripts/stop-test-services.py <worktree>...`，退出码 0 并写 STATE 摘要；这是收尾核验，不是代测，不能只看 test 报告。

目录交付状态、本地清理条件、资料核验、自动清理范围、保留分类与授权全部按 `worktrees.md`「worktree 生命周期」。每个目录须有明确处置记录；保留记录含分类（待归档或补查 / 需用户决定 / 仍在使用）、原因、保存位置、下一动作，删除后回读 `git worktree list`，不能只写「能删」，也不强行删光。目录保留不等于保留已无任务成员；成员识别与 pane 保护按 `scheduling.md`「pane 收尾」，不碰其他任务成员/进程。

统一执行：

```bash
python3 ~/.hwf/scripts/wrapup.py --repo <主仓库> --task <任务标识> --issue <发起 issue URL，没有则根 issue> --release release-<根编号> --status "<done/delivered/closed/cancelled>（说明）" --port <本交付用过的端口>...
```

可先加 `--dry-run`。退出码 0 才算完成，摘要进 STATE；退出码 1 表示残留，INDEX 未改、回执如实记录，按 `communication.md`「需要用户决定」通知，处理后重跑。脚本自身出错就报阻塞，不手写命令兜底。**INDEX 收尾状态只由脚本写，scheduler 不手改。**

只有用户明确要求关闭发起 issue，才加 `--close-request <用户评论链接>`；脚本核验该用户本人在本 issue 的评论，全部收尾通过且发回执后才关闭并回读。无参数保持打开。

脚本必须完成并回读以下证据后才写 INDEX：

1. 名下每个 worktree 的服务脚本退出码 0，本交付所有使用端口空闲；成员关闭后再执行一次。
2. 按 `scheduling.md`「pane 收尾」交叉核对成员登记、完整 `herdr pane list`、`herdr agent list`，处理本交付全部成员及无名 Agent/遗留终端，关闭后核对整份登记与实时窗格。无名身份须同时匹配登记 tab、角色标签、issue 标识，无名 Agent 还须 idle/done；身份不明或仍工作则保留并报未完成。最后一个 workspace 窗格按保护规则保留并列入回执，不能称全部关闭。
3. 按 `worktrees.md` 核验资料后删除脚本支持范围内目录，范围外按该主题判定和授权，回读 worktree 列表、记录保留项，再释放测试账号。已推送不能替代交付完成证明。
4. 发起 issue（无则根 issue）发「收尾回执」并写 STATE，作为 pane 关闭后的可查证据：

```markdown
**收尾回执**
- 测试服务：已关闭 <PID/端口列表>；端口回读 <端口…> 全部空闲（stop-test-services.py 退出码 0）
- 成员：已关闭 <登记名 / pane 列表>；agent list 回读已无本交付成员
- worktree：已删除 <路径 + 核验证据>；保留 <路径 + 分类 + 原因 + 保存位置 + 下一动作，没有写「无」>
- 分支：<开发分支是否都已推送远端，未推送的逐个列出>
- issue：<按 @用户 的要求关闭（评论链接）；没要求关闭时脚本不写这一行>
```

服务未停、成员未关、回执未发、脚本报错都不是成功，按 `communication.md`「需要用户决定」处理。依规则保留目录不自动算失败，写已保留及分类；能自行归档/补查先做，确需用户决定再通知。没回执不得改 INDEX 收尾状态。

## 9.1 arch 最终验收

风险终审判断代码风险，最终验收判断交付是不是原来要的结果。每根交付一次：全部步骤/子 issue 已汇总、完整性核对通过后，main MR 与完成/请验收评论之前；直达单 issue 同样在冒烟并汇总后执行。debug 模式不派 arch、不做此阶段。

- **单 issue 低风险直达同版本复用**：直达路径（`防风险 = 不要`、单仓库单分支）中，若 `origin/release-<根编号>` 代码树与 `§7` 经 `arch` 风险终审通过的提交完全一致（`§7` 后零代码回改、零解冲突改写）、`release-check` 退出码 `0`、且已批准用例与 `smoke` 真机截图证据全部通过，scheduler 完成 §9「交付证据核验」后在根评论与 `STATE.md` 记录 `§9.1 复用 §7 arch 已审同版本（<SHA>），真实验收与完整性核对全绿`，不重复启动第二次 `arch` 会话审同一提交。
- 方案路径、`防风险 = 要`、多仓库/多步骤，或 `§7` 后发生过任何代码回改/解冲突改写时，派 `arch` 新短会话执行最终验收（不带历史聊天；默认 15 分钟 / 25 次工具调用）：
- scheduler 准备交接包，缺任一项不派：① `planning.md` §0 判定及关键决定原文，方案路径另附已确认最终方案 snippet；② 用户过程裁定/改判 note；③ 验收条目；④ 各 issue 测试报告、截图评论、UI 走查、冒烟结果（develop MR、成功部署作业、测试环境逐条截图，或用户同意跳过 note；仅本地复核算缺项）；⑤ 汇总 SHA 及 `origin/main..release-<根编号>` diff；⑥ 待定清单；⑦ 测试后每次回改 SHA 与 code-review「是否碰到关键决定」结论行。
- arch 逐条对照关键决定/最终方案与验收点，用最终代码、测试证据写「达到 / 没达到 / 偏离」及截图链接、file:line；不重做代码评审、lint、测试，不启动服务。证据不足算没达到并列缺证；核对回改是否改变关键决定。无 develop 冒烟且无用户跳过 note，只能 `需修改`，写明「缺 develop 冒烟」。
- 最后一行独立写 `通过` 或 `需修改`；后者逐条列没达到/偏离项及改法。scheduler 原文写根评论与 STATE。
- 需修改：dev 按 `implementation.md` §6「回改打包」单趟修复留证 → code-review 增量核验（最多 2 轮）→ test 相关复测 → 重新冒烟并汇总 → arch 只复核上次未过项。arch 最终验收最多 **2 轮**；第 2 轮仍不通过，scheduler 整理项目、arch 意见、现状、可选做法交用户裁定，不开第 3 轮，不记通过。
- 未获 `通过` 或用户对剩余项明确裁定，不建 main MR、不写完成评论、不改 INDEX 收尾状态。

## 上线清单

scheduler 在根描述顶部维护区的 `## 上线清单` 维护，子 issue 不写，不另建 issue。与汇总分支同时、第一次派 dev 前建表；每次汇总更新对应仓库（新仓库加行），每次修改回读描述确认写入且用户原文未变。登记不上线不入表。main MR 经用户授权合并后不再改表，根评论记录 MR/SHA，再按 §9 关闭。

段落**只有一张表**，每仓库一行，只跟踪最终上线改动；不写发布信息、issue 列表、MR/SHA、冒烟、完整性核对、部署步骤或过程记录。

```markdown
| 仓库 | release 分支 | 改了什么 | 有没有数据库改动 |
| --- | --- | --- | --- |
| [<完整仓库路径>](https://<GitLab 域名>/<仓库路径>) | [release-<根编号>](https://<GitLab 域名>/<仓库路径>/-/tree/release-<根编号>) | <最终行为变化> | 无 |
```

- 仓库用完整路径为文字、项目首页为链接，不简称，回读时打开确认。
- release 分支用实际待上线分支名链接到分支页，用户指定则写实际值；打开确认存在，不写 SHA/MR/合并记录。
- 改了什么用一两句大白话写最终行为变化，同仓库多 issue 合成一句；不写撤回/不上线内容、内部错误码、SHA、合并记录或「无前端改动」；没改的仓库不入表。
- 数据库无改动写「无」，不留空。有 SQL 写「有：」及执行/回滚文件链接，未登记不得执行。每个 SQL 单独一行，格内用 `<br>` 不直接回车；链接用 `[文件名](完整 URL)`，避免网址吞中文标点，逐个打开确认。先按执行顺序列全部执行，再按相反顺序列全部回滚。
- 客户端本地库升版本写「无 SQL；浏览器本地库 <库名> v旧→v新」，按仓库 `AGENTS.md` 把回滚方案写决策记录并在格内附链接。
- MR/SHA/冒烟结果放各 issue 完成评论，完整性核对放根评论，部署顺序与验证放 main MR 描述。
