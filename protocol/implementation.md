# 用例与开发

实现写完再补测试，容易让测试迁就错误。本文件先固定验收用例，再用未实现时的真实失败证明测试能发现问题，独立放行后才写实现；否则不能证明开发确实按约定完成。

适用：正常交付 §4–§6、所有路径的单元测试先行，以及用户明确要求的 debug 模式。需求判定、方案与 issue 规则见 `planning.md`；角色、派活和共同评审独立性见 `scheduling.md`「角色与启动配置」「初始化」「双层评审与独立性」；后续代码评审及验收见 `review-testing.md` §7–§8。

## debug 模式

仅用户在本次需求、发起 issue 描述或评论明确要求「debug 模式」「修bug」「改bug」「极简模式」，或 `/go debug`、`/go 修bug`、`/go 改bug`、`/go 极简`、`/go minimal` 时启用（bug 前后空格不影响识别）。用户原话与来源（会话或 note 链接）记 STATE、INDEX。scheduler、成员和收件箱不得因任务简单自行启用；arch 判两个开关都不要不等于 debug。

交付顺序：本地单元测试先行与实现前核验 → dev 实现 → MR 合 develop 并等待部署 → test 在测试环境真实自动化验收 → 创建指向 `release-<根编号>` 的 MR 交用户。只取消本地端到端验收，不取消单测与实现前核验。

1. scheduler 读 issue/需求，按 `delivery.md`「根 issue 汇总分支」创建或复用 release，从它切干净开发分支、建独立 worktree、明确可写范围；按 `scheduling.md`「初始化」与 `worktrees.md`「创建与登记」执行。不派 arch、不判复杂度。先读取项目 `docs/agents/herdr-project.yaml` 的 `branches.test` 与 `smoke`；缺测试分支或可用地址即明确阻塞，不猜地址、不以本地验收代替。
2. 按普通流程的仓库职责领取新会话开发者：只改前端用 `dev-fe`，只改后端用 `dev-be`，不分端仓库用 `dev`；两端都改分别领取，模型与普通流程一致。仍按 §6 先写并运行定向单测，独立 code-review 完成实现前窄范围核验后才实现；跑相关单测、lint、type-check，不跑全量，不启动本地 Web 服务或开发版 Electron 做端到端验收。提交、push 干净开发分支。
3. scheduler 创建开发分支 → develop（项目 `branches.test`）的 MR，核对源 SHA、diff、无冲突及合并检查实际通过后即时合并；本模式启动授权包含此次测试环境 MR 合并，不含 release/main 合并，不设置自动合并。等待对应流水线部署作业成功，记录 MR、源 SHA、部署 SHA、作业链接；前后端都改须相关部署全部成功。
4. test 新会话按 `review-testing.md` §8「debug：部署后验收」到项目 `smoke` 地址逐条执行 issue 验收并留真实截图；涉及桌面原生能力另用包含本次改动、连接 develop 的测试客户端验证。不从本地启动开发服务验收。测试失败交 dev，受影响切片重做 §6 相关单测、实现前核验和修复，再合 develop、等待新部署、派 test 复测；不增加整项代码评审或 arch 终审。
5. 全部验收通过后，scheduler 用 `glab mr create` 创建干净开发分支 → `release-<根编号>` 的 MR。中文描述写关联 issue、改动、本地单测及核验、develop MR/成功部署/逐条验收证据、未验证项，注明「debug 模式：未经整项代码评审；已完成 develop 部署后自动化验收」。回读目标、源 SHA、diff，确认本需求代码与测试版本一致；只创建，不合 release/main、不关 issue。
6. 有发起 issue 则评论 release MR 链接；评论、会话回复和 ntfy 第一行均放该 MR 链接，附测试环境证据。按 `delivery.md` §9「集中收尾与回执」仅清理本任务本机进程，保留待用户合并的代码与证据，由收尾脚本将 INDEX 记为 `done（debug 模式：develop 验收通过，release MR 待用户处理）`；通知按 `communication.md`，不执行 §9.1。

develop 冲突时按 `delivery.md`「测试分支冲突与指定目标」从最新测试分支建独立集成分支，只集成本需求提交；debug 不要求整项代码评审或 arch 放行。集成分支只供测试，绝不回流干净开发分支或 release/main。核对本需求文件与干净开发分支一致；冲突处理中必要的功能改动必须回干净开发分支，重做相关单测与核验后重新集成、部署、复测，不能只修集成副本再交旧代码。

debug 不判复杂度、不写方案/spec、不单独编写/评审验收用例、不做方案确认、整项代码评审或 arch 终审、不上传 snippet。§8 的代码评审/已评审用例前置、独立本地服务启动与回改评审链不适用；部署后真实验收、截图与清理要求仍适用。单元测试先行、用例保护和实现前独立窄范围核验保持不变。测试分支、部署、地址、测试客户端或验收条件不可用时明确阻塞、列恢复动作，不自行跳过或声称本地已验证；后续改变出口须用户另行明确授权。

scheduler 不亲自写代码；全局/仓库规则继续生效，包括不在远程服务器执行命令、AGENTS.md、i18n、1000 行上限。不为过检查删改测试或跳钩子。用户要求其他 MR 目标时，先停下确认。

dev 发现需求歧义、数据迁移/存储版本/不可逆操作，或 release 冲突需取舍，立即停下报 scheduler，由 scheduler 问用户：继续 debug、从 `planning.md` §0 改走正常流程，还是放弃；不得自行切换。

## 4. 编写测试用例

适用直达根 issue 和方案根 spec。test-writer 在该 issue 新会话中按 skill `acceptance-test-cases` 编写，逐条对照 arch 提出且用户确认的验收；方案路径同时对照已确认方案/spec。本阶段只设计与准备：开发侧单元测试由 dev 在 §6 落实，最终自动化验收在代码评审通过后由 test 按 `review-testing.md` §8 执行。

用例未完成、未评审或未上传，不派开发。步骤与子 issue 按 `planning.md` §3.1 继承根需求已批准用例，由 test-writer 必要时补定向断言，不重开用例编写/评审阶段。

## 5. 用例评审：最多 3 轮

适用直达根 issue 和方案根 spec。共同独立性按 `scheduling.md`「双层评审与独立性」。precheck 可先给证据表，code-review 在独立新会话终审，只计终审轮次；test-writer、test、dev 均不得兼任终审。

code-review 按 skill `acceptance-test-cases`「评审用例」核对。test-writer 回改，scheduler 计数。通过后 scheduler 按 §5.1 上传、回填，完成前不派 dev。

第 3 轮后不启第 4 轮：arch 最终裁定有争议的验收口径，test 按裁定修正。非严重补充意见记根 issue 待定清单后继续开发；仍会假通过、不可验证或破坏数据的严重缺口，明确阻塞与最小修正项，不能用轮次上限伪造通过。

## 5.1 上传已评审测试用例

适用直达根 issue 和方案根 spec。开发前 scheduler 必须上传评审通过的版本为 GitLab 项目 snippet，回读并附 issue；未完成不派 dev。步骤和子 issue 引用根需求链接，不重复上传。可见性、安全与历史存档例外统一按 `planning.md` §2.2，使用 `internal` 并回读确认，不改 `public`。

1. 用脚本上传并回读。脚本从 `--repo` 的 origin 确定项目（不从其他 remote 推断），用 internal，描述自动补 SHA-256，回读可见性、文件名与线上内容 SHA-256，不一致退出 1：

   ```bash
   python3 ~/.hwf/scripts/upload-snippet.py create --repo <仓库路径> --file <用例文件> \
     --title "<issue IID> 测试用例（已评审）" \
     --description "<issue URL>；用例评审通过轮次 <N>；通过时间 <ISO8601>"
   ```

   上传内容与评审通过版本完全一致，上传时不改用例。以脚本输出的 `web_url`、`id`、`sha256` 为准，不以本地路径或摘要代替；之后复核用 `upload-snippet.py check`。
2. 在对应 issue 评论 URL、文件名、SHA-256、通过轮次与时间，回读确认链接和 snippet 可访问。覆盖多单至少回填父 spec，相关实现子 issue 派活均附链接。
3. dev/test 派活、代码评审交接和测试报告必须引用链接；§8 自动化对应此已评审版本。STATE 记 URL、ID、创建时间、用例 SHA、轮次及评论定位。
4. 上传失败或回读不一致即阻塞，保留本地用例和恢复信息，不跳过上传开发。

## 6. 开发人员开发

dev 在该 issue 新会话中，按确认验收、已评审用例及关键决定实现；方案路径同时遵守方案/spec。步骤和子 issue 继承根产物，不重开方案/用例阶段。开发分支从 `release-<根编号>` 切出，见 `delivery.md`「根 issue 汇总分支」；仅改约定范围。前后端都改时，dev-fe、dev-be 按 `scheduling.md`「前后端并行开发」分别执行以下顺序。

### 单元测试先行

所有开发阶段含 debug 都适用，先测试、再实现。dev 与核验者按 skill `test-first-evidence` 执行：按已评审用例（debug 按 issue 验收）写定向单测，对应实现未改时用「统一留证命令」取得有效失败，经「实现前检查点」放行才改生产代码，再绿跑与相关单测、lint、type-check，不跑全量。保持既有行为、纯文档等例外的理由与替代检查同样由独立 code-review 核对，不自行以难测免测。

**用例更正**：开发者不得自行改测后宣告通过，也不为过测弱化用例。用例错误由独立 code-review 复核；验收口径变化交 arch（debug 由 scheduler 问用户，不自行引入 arch），用户需求变化先取用户确认。批准后才改，保留前后版本与审批，重新取得有效实现前证据；已评审文档变化同步 snippet、SHA。

完成条件：实现逐条对应验收，开发相关检查通过，先行证据与用例变更审批（有则）齐全；交接 HEAD/diff、命令、结果、未验证项。提交、push、合并遵守当次明确授权和仓库 Git 规则；新会话沙箱限制以实际错误为准。

### 实现前检查点

每个可独立验证的行为切片按「只写测试 → 有效失败 → 独立核验 → 实现」推进，不按每条断言派评审，也不先写完整实现再补测。

1. **测试阶段授权**：scheduler 首次派 dev 只授权本切片测试准备、测试代码和取证，列验收编号、生产文件范围。dev 按 skill `test-first-evidence` 交证据后等放行，之前不得编辑对应生产代码。确实无法到达断言时交独立 code-review 核对，必要时 arch 决定验证方式（debug 由 scheduler 问用户），不自行加生产占位实现绕过。
2. **独立窄范围核验**：code-review 按 skill `test-first-evidence`「核验者」判定有效失败，在 `reviews/` 留结论「允许实现」或「先修测试准备」；只核该切片，不做整项评审，不计 §7 轮次。
3. **记录与放行**：scheduler 将结论路径、允许修改范围记 STATE 后才续派实现。测试/验收口径变化按「单元测试先行」的用例更正审批、重核受影响切片；旧放行不自动覆盖新用例。
4. **失败分流**：准备问题只修准备再取证。只有需求待澄清、权限等外部条件需用户处理时才联系；普通准备修复与放行记录留任务内，不逐次打扰。
5. **发现先写实现**：按 skill 立即停切片并保留事实；历史缺证仍缺，取得用户对此缺口的例外授权前，不关闭开发阶段、不最终放行。既有明确批准的例外按原授权范围有效，不重复申请、不扩展；历史详见原 issue/Git。

直达、方案、子步骤和 debug 均适用。debug 不做整项代码评审，但必须做本窄核验及 develop 部署后验收。留证脚本只记事实，不判断业务失败原因，脚本非零不等于独立核验通过。

### 统一留证命令

每次红跑/绿跑统一用 `scripts/test-evidence.py` 保存当时源码并直接运行测试进程，用法与证据要求见 skill `test-first-evidence`「留证命令」。交接整个证据目录，不手拼留证命令，不只交日志或最终提交号；快照/日志只存任务授权本地目录，不直接上传 GitLab。

交付证据与共用产物只保留一份，按 `planning.md`「文档最小化」维护。
