# 用例与开发

实现写完再补测试，容易让测试迁就错误。本文件先固定验收用例，再用未实现时的真实失败证明测试能发现问题，独立放行后才写实现；否则不能证明开发确实按约定完成。

适用：正常交付 §4–§6、所有路径的单元测试先行，以及用户明确要求的 debug 模式。需求判定、方案与 issue 规则见 `planning.md`；角色、派活和共同评审独立性见 `scheduling.md`「角色与启动配置」「初始化」「双层评审与独立性」；后续代码评审及验收见 `review-testing.md` §7–§8。

## debug 模式

仅用户在本次需求、发起 issue 描述或评论明确写「debug 模式」「改bug」、`/go debug`、`/go 改bug` 时启用；旧叫法「极简模式」、`/go 极简`、`/go minimal` 仍算。用户原话与来源（会话或 note 链接）记 STATE、INDEX。scheduler、成员和收件箱不得因任务简单自行启用；arch 判两个开关都不要不等于 debug。

交付范围只有：dev 开发 → 提交目标为 `release-<根编号>` 的 MR，到此结束。

1. scheduler 读 issue/需求，按 `delivery.md`「根 issue 汇总分支」创建或复用 release，从它切开发分支、建独立 worktree、明确可写范围；按 `scheduling.md`「初始化」与 `worktrees.md`「创建与登记」执行。不派 arch、不判复杂度。
2. 用 `member-start.py dev-mini` 派新会话开发者；前后端都改，分别领 `dev-fe-mini`、`dev-be-mini`，不领 dev/dev-fe/dev-be。只做需求改动，仍按 §6 先写并运行单元测试、取得实现前放行后再实现；跑相关 lint、type-check 和聚焦检查，不跑全量测试，在本 worktree 提交、push。
3. scheduler 用 `glab mr create` 建 MR，目标只能 `release-<根编号>`。中文标题/描述写改动、关联 issue、dev 实跑检查与结果、未验证项，必须注明「debug 模式：未经代码评审与自动化测试」。回读目标、源分支和 diff。不合并 MR、不合 develop。
4. 有发起 issue 则评论 MR 链接；评论、会话回复和 ntfy 第一行均放 MR 链接。INDEX 写 `done（debug 模式：MR 已提交，待用户处理）`，按 `communication.md`「通知模式」通知后停止。

debug 不判复杂度、不写方案/spec、不单独编写/评审验收用例、不做方案确认、整项代码评审、§8 自动化/浏览器验收，不上传 snippet、不合 MR、不关 issue。单元测试先行、用例保护和实现前独立窄范围核验仍适用。后续合并或补独立验收由用户决定，按用户之后的当次指示执行。

scheduler 不亲自写代码；全局/仓库规则继续生效，包括不在远程服务器执行命令、AGENTS.md、i18n、1000 行上限。不为过检查删改测试或跳钩子。用户要求其他 MR 目标时，先停下确认。

dev 发现需求歧义、数据迁移/存储版本/不可逆操作，或 release 冲突需取舍，立即停下报 scheduler，由 scheduler 问用户：继续 debug、从 `planning.md` §0 改走正常流程，还是放弃；不得自行切换。

## 4. 编写测试用例

适用直达根 issue 和方案根 spec。test-writer 在该 issue 新会话中，逐条对照 arch 提出且用户确认的验收；方案路径同时对照已确认方案/spec。

每条保留验收编号，写前置条件、输入/操作、预期结果、失败判据、数据准备/清理、自动化方式、证据要求。覆盖主路径、边界、错误、回归及适用权限/兼容性，明确直接相关测试文件/目录，不跑全量套件。页面、组件、样式或布局变更必须有 UI 走查：有稿对照视觉呈现，无稿核对布局整齐。

用例和可提前编写的自动化脚本落盘，记运行命令与环境。本阶段只设计与准备，面向被验功能的最终自动化在代码评审通过后执行。区分：

- 开发侧单元测试：输入、预期输出、边界，dev 在 §6 先落实为可运行测试。
- 最终自动化验收：用户操作与可观察结果，test 在 `review-testing.md` §8 执行。

用例未完成、未评审或未上传，不派开发。步骤与子 issue 按 `planning.md` §3.1 继承根需求已批准用例，由 test-writer 必要时补定向断言，不重开用例编写/评审阶段。

## 5. 用例评审：最多 3 轮

适用直达根 issue 和方案根 spec。共同独立性按 `scheduling.md`「双层评审与独立性」。precheck 可先给证据表，code-review 在独立新会话终审，只计终审轮次；test-writer、test、dev 均不得兼任终审。

code-review 核对逐条验收覆盖（方案路径还覆盖 spec）、假通过判据、可复现性与清理安全。test-writer 回改，scheduler 计数。通过后 scheduler 按 §5.1 上传、回填，完成前不派 dev。

第 3 轮后不启第 4 轮：arch 最终裁定有争议的验收口径，test 按裁定修正。非严重补充意见记根 issue 待定清单后继续开发；仍会假通过、不可验证或破坏数据的严重缺口，明确阻塞与最小修正项，不能用轮次上限伪造通过。

## 5.1 上传已评审测试用例

适用直达根 issue 和方案根 spec。开发前 scheduler 必须上传评审通过的版本为 GitLab 项目 snippet，回读并附 issue；未完成不派 dev。步骤和子 issue 引用根需求链接，不重复上传。可见性、安全与历史存档例外统一按 `planning.md` §2.2，使用 `internal` 并回读确认，不改 `public`。

1. 使用 origin 项目，不从其他 remote 推断：

   ```bash
   glab snippet create -R <origin GROUP/REPO> \
     --title "<issue IID> 测试用例（已评审）" \
     --filename "<用例文件名>" \
     --visibility internal \
     --description "<issue URL>；用例评审通过轮次 <N>；通过时间 <ISO8601>" \
     <用例文件>
   ```

   上传内容与评审通过版本完全一致，上传时不改用例。
2. 取得 ID/URL，用 `glab api projects/:fullpath/snippets/<id>` 回读 `web_url` 与文件内容，核对 SHA-256 与评审通过版本一致，不以本地路径或摘要代替。
3. 在对应 issue 评论 URL、文件名、SHA-256、通过轮次与时间，回读确认链接和 snippet 可访问。覆盖多单至少回填父 spec，相关实现子 issue 派活均附链接。
4. dev/test 派活、代码评审交接和测试报告必须引用链接；§8 自动化对应此已评审版本。STATE 记 URL、ID、创建时间、用例 SHA、轮次及评论定位。
5. 上传失败或回读不一致即阻塞，保留本地用例和恢复信息，不跳过上传开发。

## 6. 开发人员开发

dev 在该 issue 新会话中，按确认验收、已评审用例及关键决定实现；方案路径同时遵守方案/spec。步骤和子 issue 继承根产物，不重开方案/用例阶段。开发分支从 `release-<根编号>` 切出，见 `delivery.md`「根 issue 汇总分支」；仅改约定范围。前后端都改时，dev-fe、dev-be 按 `scheduling.md`「前后端并行开发」分别执行以下顺序。

### 单元测试先行

所有开发阶段含 debug 都适用，先测试、再实现：

1. **先写测试**：按已评审用例编写/补充定向单测，再开始对应生产代码新增/修改；debug 按 issue 验收。已有测试覆盖则直接复用，不重复造用例，不先实现再补测冒充先行。
2. **先运行留证**：对应实现未改时，用「统一留证命令」运行。新增行为/修缺陷必须看到目标断言因未实现或缺陷仍在而失败；环境、依赖、语法错误不算。保持既有行为的改造可用通过测试锁定行为，记录为何无需新增失败。纯文档等无可单测行为，开发前记原因与替代检查，由独立 code-review 核对；不造无意义测试，不自行以难测免测。
3. **放行再实现**：先完成「实现前检查点」，取得本切片放行记录后才改生产代码。只修实现使确认测试通过，运行相关单测、lint、type-check 等聚焦检查，不跑全量。交接附实现前/后证据、对应测试版本和放行记录，缺先行证据不得称完成。
4. **保护用例**：失败先查实现，不为过测改预期、放宽断言、删除/跳过失败用例、用必过 mock 替代真实逻辑、更新快照迎合错误。确有用例错误，先停对应实现，提交验收依据、原断言、失败输出、拟改内容/理由，由独立 code-review 复核；验收口径变化交 arch，用户需求变化先取用户确认。批准后才改，保留前后版本与审批，重新取得有效实现前证据；已评审文档变化同步 snippet、SHA。开发者不得自行改测后宣告通过。

完成条件：实现逐条对应验收，开发相关检查通过，先行证据与用例变更审批（有则）齐全；交接 HEAD/diff、命令、结果、未验证项。提交、push、合并遵守当次明确授权和仓库 Git 规则；新会话沙箱限制以实际错误为准。

### 实现前检查点

每个可独立验证的行为切片按「只写测试 → 有效失败 → 独立核验 → 实现」推进，不按每条断言派评审，也不先写完整实现再补测。

1. **测试阶段授权**：scheduler 首次派 dev 只授权本切片测试准备、测试代码和取证，列验收编号、生产文件范围。dev 交 `run.json`、原始日志、源码快照、测试文件、目标断言位置，说明期望/实际/为何目标功能导致失败，然后等放行；之前不得编辑对应生产代码。接口或模块不存在的导入/编译失败不算行为失败，先调测试边界；确实无法到达断言时交独立 code-review 核对，必要时 arch 决定验证方式，不自行加生产占位实现绕过。
2. **独立窄范围核验**：code-review 只核该切片验收、测试、日志、实现前源码，不做整项评审，不计 §7 轮次。有效失败须同时满足：成功收集测试并进入目标断言；证明未实现或缺陷仍在；无夹具、依赖、语法、导入、权限、服务故障遮住结果；留证脚本无错、`source_unchanged=true`；真实退出码非零且与日志一致；快照证明实现未改。`--phase red`、非零码或 FAIL 不能单独作依据。
3. **记录与放行**：复核者在 `reviews/` 留验收编号、测试/源码指纹、证据路径、失败断言、结论「允许实现」或「先修测试准备」。保持既有行为、纯文档等例外也在此核验理由与替代证据，不强造失败。scheduler 将结论路径、允许修改范围记 STATE 后才续派实现。测试/验收口径变化按「单元测试先行」第 4 条审批、重核受影响切片；旧放行不自动覆盖新用例。
4. **失败分流**：准备问题只修准备再取证；期望已满足先查无需改代码或选错测试，不故意破坏实现造红。只有需求待澄清、权限等外部条件需用户处理时才联系；普通准备修复与放行记录留任务内，不逐次打扰。
5. **发现先写实现**：立即停切片，保留代码、日志和事实，不删历史、不倒退重跑冒充先行。可补测试验证当前行为，但历史缺证仍缺；取得用户对此缺口的例外授权前，不关闭开发阶段、不最终放行。既有明确批准的例外按原授权范围有效，不重复申请、不扩展；历史详见原 issue/Git。

直达、方案、子步骤和 debug 均适用。debug 仍不做整项代码评审、§8 验收，但必须做本窄核验。留证脚本只记事实，不判断业务失败原因，脚本非零不等于独立核验通过。

### 统一留证命令

每次红跑/绿跑统一用 `scripts/test-evidence.py` 保存当时源码并直接运行测试进程，交接整个证据目录；不手拼留证命令，不只交日志或最终提交号。

```bash
python3 ~/.hwf/scripts/test-evidence.py \
  --repo <被测仓库根目录> --out <每次运行独占的新证据目录> \
  --case <验收编号> --phase red \
  -- go test ./internal/service -run '^TestTargetBehavior$' -count=1
```

- 绿跑用 `--phase green` 和另一个新目录。`--` 后直接测试程序及参数，不包 `sh -c`、管道、`; tail`、`; echo`。日志另读 `output.log`，查看日志的退出码不是测试结果；阶段标签不判业务红，仍查原始输出，整个进程失败不因某用例 PASS 算绿。
- 测试前保存 `source.tar`（实际工作树文件，含暂存后又改内容、未忽略新文件、符号链接）、`source.json`（指纹与删除记录）、HEAD、暂存/未暂存补丁、Git 状态；测试后保存原始输出、真实退出码、起止时间、源码变化检查到 `run.json`。查看快照解包到新建空目录，不覆盖工作树。
- 输出目录在仓库外或被 Git 忽略，已有目录拒绝覆盖。快照不含 `.git`、忽略的依赖/本地配置，不承诺重建外部服务或环境；另记版本和非敏感准备。忽略的源码不算覆盖；子模块先明确独立仓库取证范围，遇 gitlink 脚本拒绝运行，不静默漏存。
- 测试期间独占 worktree，不并行改源码；测试会改源码先消副作用。前后源码或 HEAD 变化证据无效、返回 125；执行前留证失败不启动测试。正常透传测试退出码，信号终止映射 `128 + 信号号`；原始码在 `run.json`，不只按外层命令是否成功判断。
- 快照/日志可能敏感，只存任务授权本地目录，不直接上传 GitLab。脚本记命令参数、不记环境变量，凭据不得放参数。用例更正仍先审批；事后重跑不能冒充补齐历史先行证据。

交付证据与共用产物只保留一份，按 `planning.md`「文档最小化」维护。
