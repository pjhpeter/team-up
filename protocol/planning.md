# 需求判定、方案与 issue

做法和验收没说清就开发，容易返工。本文件先让 arch 查清现状、风险与验收，再让用户确认；需要方案时才走方案阶段。这样既不跳过必要检查，也不因工作量大而增加流程。

适用：正常交付的 §0–§3、需求拆分、issue 与标签维护。用户明确要求 debug 时改读 `implementation.md`「debug 模式」。角色初始化、派活、记录与共同评审独立性见 `scheduling.md`「角色与启动配置」「初始化」「双层评审与独立性」；通知、用户确认与输出两层格式见 `communication.md`「通知模式」「需要用户决定」「原文与材料」。

## 0. 复杂度判定：两个开关

scheduler 组建团队后、进入方案前，派 arch 在该 issue 的新会话中判定并写「需求理解卡」。只读，不写方案、不执行实现；默认预算 25 分钟 / 40 次工具调用。派活只引用本节，要求按本节卡片、开关、口径和输出格式作答，不得另写或缩减判定标准。本阶段不计入方案、用例或代码评审轮次，不创建周期性监控。模型与临时替换授权按 `herdr/config.yaml` 及 `scheduling.md`「双层评审与独立性」。debug 不走本阶段。

### 需求理解卡

arch 先查清以下三项，再判开关；用户在 §0.1 一并确认。

1. **现状**：入口 → 关键模块 → 数据去向、可直接复用的能力、会经过的公共代码。按仓库规则先查代码关系图再读源码，每条附 `file:line`；查到能回答「改这里会连带影响谁」，不只读需求点名文件。
2. **历史与坑**：必查相关文件的 `git log` / `git blame` 及对应 MR、issue，issue 跟踪里的关联 issue 与评论，共用记忆库 `~/.agents/memory/<项目>/MEMORY.md` 的相关条目。分别写查到什么，列出「不能动或动了要一起处理」的写法与出处（提交 SHA、issue 链接或记忆条目名）。没有记录时写「已查 <查了什么>，无相关记录」，不留空。
3. **验收条件**：编号列表，每条一个用户能看到或能测到的结果，格式为 `<结果> ｜ 证据：<怎么证明>`。必须能一致判定过/不过；证据具体到页面操作后的截图、接口返回字段、定向测试或命令输出。需求每个目标至少对应一条；不做的范围放进关键决定。「体验更好」「显示正常」须改成具体现象。验收说不清且代码也定不了时，先澄清。

### 开关与触发条件

| 开关 | 回答什么 | 判「要」后增加什么 |
| --- | --- | --- |
| **先出方案** | 做法清不清楚？ | §1–§3，再进所有正常路径共用的 `implementation.md` §4–§5.1 |
| **防风险** | 出错能否撤回、是否波及本功能以外？ | 回滚方案、上线顺序、上线清单及兼容/回滚核对 |

两个开关独立，默认「不要」。判「要」必须写具体触发项与证据（`file:line`、接口文档或 issue 原文）；拿不准、求稳、怕担责不能替代证据，确实命中也不得为了省流程判「不要」。按难度与风险判，不按工作量判。

**先出方案：要**，命中任一：

1. **做法不唯一、当场定不了**：至少两条差别很大的可行做法，换一条要推倒重来；arch 查证后仍需比较、讨论、试验或原型才能决定。列明各条做法与为什么现在定不了。文案、字段名、组件拆法等细节不算。
2. **架构改造**：必须做下列任一改造，并说明为何不能在本功能内局部解决：
   - 改模块边界、分层或依赖方向，拆合模块，引入核心子系统；
   - 改全局机制并改变其他模块或所有调用方行为，如请求层、路由守卫、全局状态、鉴权/会话/token；
   - 改已有跨模块/跨端契约语义，须多个模块或前后端同步改造，如接口/字段含义或同步/传输协议；
   - 核心数据模型结构性重组，改变实体组织或数据归属，须迁移已有数据并改多处读写路径。

arch 能当场决定的选择写入「关键决定」，不因此判「要」，也不设数量上限。决策点是开发前要定、不同选项会改变实现结构或影响范围的选择，同一决定的细节不另计。先查局部请求选项、composable、组件等可复用机制，不得未经查证假定必须改全局。

**防风险：要**，命中任一：

1. **撤不回**：改写/删除已有数据、回填存量数据、改变已有字段含义、本地存储升版本，或重新发版也恢复不了的操作。
2. **要按顺序上线**：前后端或多服务须按特定顺序部署，否则旧版调用新版出错，如已有接口参数/返回语义变化、数据库迁移先于代码。
3. **波及本功能以外**：改变已有公共接口/字段语义、权限规则（放宽或收紧）、新增依赖、调整构建/发布配置，或改其他模块、所有用户共同经过的公共代码路径。

未命中就判「不要」。例如本功能内改逻辑或修 bug；在不改变既有读取方式时给返回类型加字段；新增接口函数、错误码枚举、多语言文案；新建表或加可空/有默认值字段且无需特定上线顺序；调用后端已实现安全控制的密码、验证码、绑定/换绑邮箱手机号等接口。

### 判定口径

本口径与触发项字面冲突时，以本口径为准：

- 文件数量、代码行数、步骤数量、耗时不作依据；几十个语言文件的同类机械改动也不判「要」。直达路径单 issue，工作量大不是拆 issue 的理由。
- 前后端都改，在同一 issue 内分前端、后端步骤并行，按 `scheduling.md`「前后端并行开发」执行；本身不触发任一开关，须特定上线顺序才触发对应防风险项。
- 真实后端与浏览器验证是 `review-testing.md` §8 的通用要求，不作判「要」的理由。
- 本功能内能解决的取舍（本功能接口选项、store 专用新字段等）写关键决定，不算架构改造。
- 数据库迁移不自动触发先出方案：看是否核心数据模型结构性重组；撤不回、特定上线顺序另按防风险判断。
- 接口已定的证据，满足任一即可：issue 有路径、请求/响应字段与错误码；接口文档、后端代码或 spec 可查；用户明确说后端已完成。字段或错误语义缺失则先澄清。

### 先澄清与防风险措施

需求歧义、验收不清或依赖后端接口缺字段/错误语义时，arch 不判开关，输出 `复杂度判定：待澄清`，每个问题附选项与建议。scheduler 按 `communication.md`「需要用户决定」提问；issue 发起的任务在发起 issue 评论并 @发起人，再发终态通知；INDEX 写 `blocked（等用户澄清需求）`。答复记入 issue 与 STATE，再派 arch 重判。需求不清不构成先出方案的理由。

防风险为「要」时，所有路径执行：

- 关键决定包含回滚方案（如何退回、哪些数据退不回）与上线顺序（没有写「无」）。
- 登记根 issue 上线清单；涉及数据库或本地存储，在「有没有数据库改动」格附链接。维护规则见 `delivery.md`「上线清单」。
- `review-testing.md` §7 加核回滚可执行性、新旧版本混跑安全；§8 在验收用例外加测触发项对应兼容场景，如旧前端调新后端、升版本后读旧数据。不能自动化时记录原因与替代证据。

### 输出与落盘

字段名一字不改，放在 `## 完整内容` 中，字段单独成行或作小标题。实际回复用普通 Markdown，不包代码块；前面的 `## 给用户的摘要` 只写判定、一两句理由和待用户决定事项。验收由 scheduler 在 §0.1 单独贴出，不抄进摘要。

```text
复杂度判定：<直达路径|直达路径 + 防风险|方案路径|方案路径 + 防风险|待澄清>
先出方案：要|不要（要：开关一第几项、各做法或哪项架构改造、为什么现在定不了 / 不能局部解决）
防风险：要|不要（要：开关二第几项及证据）
理由：<一两句人话>
依据：<issue URL / file:line / 命令输出>
现状：<需求理解卡第 1 项，每条附 file:line>
历史与坑：<需求理解卡第 2 项，三处各查到什么、不能动的写法及出处>
验收条件：<需求理解卡第 3 项；编号，每条「<结果> ｜ 证据：<怎么证明>」；待澄清写已确定部分>
关键决定：<没有写「无」；每条「决定 / 理由 / 影响范围 file:line」，不写完整方案；防风险为要必须含回滚方案与上线顺序>
接口约定：<前后端都改时必填：路径与方法、请求字段、返回字段、错误码与含义、旧前端调用新后端会怎样；否则「无」>
待澄清问题：<待澄清必填：问题、可选答案与建议>
```

非待澄清判定，scheduler 先运行：

```bash
python3 ~/.hwf/scripts/task-record.py card-check --file <判定落盘文件>
```

脚本检查现状的 `file:line`、非空历史与坑、每条验收证据，通过时打印验收原文。退出码 3 时原样交回 arch 同一会话补齐，之前不得发 §0.1 确认或派开发；scheduler 不补写。通过后把判定、需求理解卡和关键决定原文写入 STATE，并记入来源 issue 评论或直达路径 issue 正文，不只口头传递。

## 0.1 用户确认复杂度判定

arch 判完开关必须停下请用户确认，确认前不进任何路径。待澄清先按 §0 澄清；debug 不走本节。本检查点不计评审轮次，开发中改判也须重新确认。

1. 在发起 issue（没有则来源或根 issue）评论并 @发起人；非 GitLab 发起则在调度会话提出同样内容：

   ```markdown
   **复杂度判定：<直达路径|直达路径 + 防风险|方案路径|方案路径 + 防风险>（等你确认）**

   <member-settle.py 生成的 .comment.md 全文：arch 摘要在前，完整判定折叠>

   **做完以后按这些条件验收（不对请直接指出第几条）：**
   <card-check 打印的验收条件原文，不改写、不删减>

   接下来会怎么走：<一句人话>

   请回复：「同意」按这个判定和验收条件推进；或「改成 先出方案：要/不要、防风险：要/不要」并说明原因；或指出要改的验收条件、补充需求让架构师重新判定。
   ```

   不改写/删减 arch 判定。进度标签改 `状态:等你处理`，INDEX 写 `blocked（等用户确认复杂度判定）`，按 `communication.md`「需要用户决定」发 ntfy，正文带评论链接。
2. 等明确认可：「同意」「可以」「没问题」「按这个来」算；「收到」「好的我看看」不算，不确定就问「按<判定>推进吗？」。确认前不派 arch-lite/dev/test、不建实现 issue、不写 spec。
3. 同意：确认 note 链接记 STATE，按判定推进。用户改判：以用户为准，STATE 记原判定 → 新判定及原因；防风险改「要」但缺回滚/顺序时先派 arch 补齐，**再次确认**；先出方案改「要」进 §1，两个都「不要」进 `implementation.md` §4，不直接开发。用户补需求：写 issue 与 STATE、派 arch 重判、重新确认。

### 路径与改判

- **直达路径**：单 issue，优先来源 issue，没有则在 origin 项目按仓库 issue 规则（如 `docs/agents/issue-tracker.md`）建实现 issue，写范围、验收、测试方式、依赖，打 `需求` 与当前进度标签。不建 spec、不拆子 issue、不补写或确认方案。验收原样使用已确认理解卡，scheduler 不自拟。关键决定、现状、历史与坑原文记 issue、STATE 并附 dev 派活。只跳过 §1–§3，继续 `implementation.md` §4 → §5 → §5.1 → §6、`review-testing.md` §7 → §8、`delivery.md` §9。§7 核对关键决定、历史约束与影响范围，§8 执行开发前已评审用例；真实浏览器、截图和服务清理要求不变。
- **方案路径**：根 spec 走 §1–§9；步骤或子 issue 继承批准方案与用例，从 §6 开始。防风险为「要」时技术方案覆盖回滚与上线顺序，两种路径均执行防风险措施。
- **改判**：直达中任一角色发现命中开关一，或命中开关二但原判「不要」，立即停下报 scheduler，由 arch 复核。只补风险则补回滚/顺序，先出方案改「要」则从 §1 重进；均先经 §0.1 用户确认再继续。工作量或范围变大但未命中不改判。需求/接口与约定不符则先澄清，不因此改判。已有开发/评审不自动计入方案/用例轮次，原因与返工记 STATE。
- **责任**：arch 对分流负责；scheduler 只核记录与路径一致。成员或 scheduler 认为判错，升级请 arch 复核，不自行改判或越过。

## 1. 编写技术方案

方案作者为 arch-lite；执行体、model、thinking 读取 `herdr/config.yaml` 的该 profile，不依赖执行体默认值，不擅自替换。arch 负责独立评审、关键取舍、严重争议裁决、代码最终风险闸门与最终验收，不编写或回改方案。会话独立性与临时模型替换授权按 `scheduling.md`「双层评审与独立性」；换 profile/模型不构成独立。

scheduler 派活附需求理解卡。arch-lite 从现状、历史与坑出发核对补充，不从零重查；按仓库要求先查 Graphify 再查源码。方案至少包含目标、范围、现状、模块/接口变化、数据/状态流、兼容性、风险、验证方式、必要拆分建议、逐文件改动、回滚与验证表；逐条说明如何满足验收及处理历史约束，增改验收须单列原因。

arch-lite 负责初稿与按意见回改，不自审、不签发、不拍板；arch 按双层评审签发，precheck 只出证据。方案落盘，标明版本与来源。STATE 记录实际 model/thinking、编写会话、方案版本；终审注明参考版本；记录编写/评审 turns/cost、返工轮次与严重漏检，扩展和成本结论由用户按实测决定。

完成条件：全部目标与关键边界覆盖，评审者可凭方案及源码独立评审。

## 2. 方案评审：最多 5 轮

共同评审独立性按 `scheduling.md`「双层评审与独立性」。本轮可由 precheck 先出证据表，arch 独立判断后复核终审，只计 arch 的轮次。

每轮 arch 给明确问题、严重度、证据、修正建议；arch-lite 回改，scheduler 记轮次与决定。第 5 轮后不启第 6 轮，不因意见未一致拖住流程：

- 剩余严重意见，scheduler 整理意见、双方理由、风险与选项，交用户裁定，作者不得自行裁定。
- 非严重意见由 arch 拍板。
- 采用/不采用、裁定人、理由、风险、最终版本写决策记录，交 scheduler。

arch 可以决定取舍，不能把客观不可执行、验收证据缺失或数据破坏风险说成通过；推进不了须给具体阻塞与恢复动作。

## 2.1 用户确认最终方案

评审通过后仍不得进入 spec、用例或开发。arch-lite 合并最终方案，arch 复核关键取舍并写决策记录；scheduler 先按 §2.2 上传「待确认」snippet 并回读，再请用户确认。

确认请求第一行必须为最终方案 snippet 链接，随后给方案 SHA、目标/范围、关键取舍与用户裁定项、未关闭风险、方案要求的实测检查点、下一步计划。只有本地路径或 SHA 不算提交。停下前按 `communication.md`「需要用户决定」发送 Herdr ntfy `⚠️ 需要处理`；2xx 才算成功，失败最多一次有界重试并如实报告。

- 用户明确「确认/按此实现」后，按 §2.2 标为已确认、回填 issue，再进 §3。
- 用户要求修改，由 arch-lite 改、arch 核取舍，另传新版待确认 snippet 后重新确认。反馈不计 5 轮；触及契约、数据安全或验收口径可定点复核并记录，不重开完整轮次。新严重问题仍交用户裁定。
- 未答复保持 blocked，不以评审通过、CI 绿或时间压力越过。仅当前任务的用户明确放弃可豁免，授权记 STATE 与 issue。
- 直达路径无技术方案，不适用本检查点；§0.1 后进 `implementation.md` §4，不另加方案确认。

## 2.2 上传最终方案与 snippet 可见性

方案在用户确认前上传项目 snippet，确认后标记同一个 snippet 并附 issue。方案与测试用例统一使用 `internal`：不是仅项目成员可见，受 GitLab 项目与用户访问规则约束；不得上传凭据或敏感数据、不得改 `public`。上传后回读 `visibility=internal`。此规则只管后续上传，不批量改历史 snippet，不撤销用户给单项任务指定的其他存档方式。

1. 用脚本上传并回读。脚本从 `--repo` 的 origin 确定项目（不凭其他 remote 推断），用 internal，描述自动补 SHA-256，回读可见性、文件名与线上内容 SHA-256，不一致退出 1：

   ```bash
   python3 ~/.hwf/scripts/upload-snippet.py create --repo <仓库路径> --file <方案文件> \
     --title "<issue IID> 最终技术方案 r<N>（待确认）" \
     --description "<issue URL>；待用户确认"
   ```

   上传内容与提交确认版本完全一致；修改后另建新版 snippet，不覆盖旧版。
2. 以脚本输出的 `web_url`、`id`、`sha256` 为准，通过后才发确认，会话、issue 评论和 ntfy 均附 `web_url`，不拿本地路径或摘要代替。
3. 用户确认后标记同一个 snippet。脚本先核对线上内容与确认版本一致才改标题和描述，改完回读；不一致退出 1，此时不得标记，重传并重新确认：

   ```bash
   python3 ~/.hwf/scripts/upload-snippet.py mark --repo <仓库路径> --id <snippet ID> --file <确认版本文件> \
     --title "<issue IID> 最终技术方案 r<N>（已确认）" \
     --description "<issue URL>；确认时间 <ISO8601>；来源 <note 链接>"
   ```

   再在发起 issue 评论 URL、文件名、SHA-256、确认时间；回读评论及 snippet 可访问性。
4. spec 与实现子 issue 带同一已确认链接；STATE 记 URL、ID、创建/确认时间、方案 SHA 与评论定位。
5. 上传失败或回读不一致即阻塞，保留本地方案与恢复信息；无链接不请确认，不跳过上传进 spec。

## 3. 编写 spec 与 GitLab issues

方案确认后，scheduler 编中文 spec：背景、目标、非目标、用户可见行为、实现边界、接口/数据约束、验收标准、测试范围、依赖与方案链接。验收以理解卡加最终确认的增改为准，保留 `<结果> ｜ 证据：<怎么证明>`。优先 `to-spec` 模板与发布流程，不具备时按仓库 `docs/agents/issue-tracker.md` 等价执行。

发布前读仓库 issue-tracker、triage-labels 和适用写作规则；优先 glab，从 origin 确认 host/project。spec 为根 issue，打 `需求` 与当前进度标签，回读标题、正文、标签、URL 并记录。

- 不必拆则直接执行 spec。须拆则按 `to-tickets` 的 tracer-bullet（可独立验证的纵向步骤）和阻塞边规则；无 skill 则按同规则手工切。其「每片一 issue」默认不适用：范围、验收、测试与 `Blocked by 步骤 <序号>` 写根 issue 进度；只有 §3.1 条件命中才建子 issue，写 Parent、Blocked by，优先原生关系，不可用则描述中显式维护。粒度由 arch 确认，不另找用户。
- 先查现有 issue 复用，防重复创建；继承来源 milestone。子 issue 打 `子任务` 与当前进度，不打 `需求`；保留 `herdr-auto`。
- 先执行无阻塞的叶子 issue；父 spec 不和子 issue 竞争；独立并行、依赖按序。

完成条件：spec、子 issue 均可通过实际 URL 回读，每步验收可判定、依赖明确、方案决策关联。

## 3.1 步骤与子 issue

最多两层：根 spec → 步骤或子 issue，不再建下一层。默认步骤写根 issue「进度」勾选列表；每步仍有开发分支 `feat|fix/issue-<根编号>-s<序号>-<简述>`、MR、新会话、代码评审、测试，走 §6–§9。证据写根 issue 评论，关闭动作对应勾选步骤。

仅下列任一条件可建子 issue：与其他步骤同时开发，需独立 worktree 和写者；另一个仓库由另一组成员负责；用户明确要求单独建单。直达路径仍遵守 §0 单 issue 的规则。

dev 认为过大，向 arch 提交拆分理由、拟拆步骤、依赖和验收；arch 确认后 scheduler 改成同层步骤（如 3 → 3a、3b），不加层级；理由和结论记 STATE、根 issue 评论。未确认则按原范围继续，或 arch 重划范围/报阻塞。

步骤与子 issue 继承根 spec 已批准方案与用例，不重走 §1、§2、§2.1、§2.2、§4、§5、§5.1，直接 `implementation.md` §6 → `review-testing.md` §7–§8 → `delivery.md` §9。必要定向断言由 test-writer 补，不另设用例评审轮次；浏览器、截图、独立服务与清理要求不变。根 spec 的完整方案/用例阶段不降级。

## issue 数量与进度标签

issue 只给要做的活，记录放评论。每张 open issue 恰好一个 `状态:` 标签。

### 开单与问题分流

只在三种情况开 issue：用户新需求开根 issue（`需求`）；符合 §3.1 的步骤开子 issue（`子任务`）；用户明确要做的待定/登记条目开新根 issue，并在原条目附新链接。上线清单写根 issue 描述；非严重意见/残留进待定清单；无关问题、既有缺陷、测试债、基线红灯进登记池；移植其他分支作为根 issue 步骤，均不另开 issue。

新问题只问「不修，本次验收能否通过」：有关且影响验收，在当前步骤直接修，不另记/开单；有关但不影响验收，记待定清单；无关，进登记池，不修、不排期、不派人，修测试也不顺手改生产代码。每种都在会话一句话告知发现什么、有关/无关、记在哪里；拿不准按无关并说明，由用户决定。

### 根 issue 维护区

首次派 dev 前，scheduler 用 `task-record.py progress --issue <根 URL> --steps-file <步骤 JSON>` 在描述最上面建维护区，用户原文一字不改放下方。之后「进度」只由脚本写，禁止手改描述里的进度段；「上线清单」表仍按 `delivery.md` 手动维护，脚本原样保留。

```markdown
<!-- hwf:start 以下由交付流程维护 -->
## 进度

**现在**：页面改版开发中，代码评审第 2 轮
**下一步**：评审通过后合 develop 冒烟
**等你处理**：无

_更新于 2026-11-19 15:30；勾选表示代码已进 `release-<根编号>`，细节见评论_

- [x] 1. 接口接入（已在 release-<根编号>）
- [ ] 2. 页面改版　Blocked by 1
- [ ] 3. 桌面端移植 → #<子编号>（子 issue）

## 上线清单
| 仓库 | release 分支 | 改了什么 | 有没有数据库改动 |
| --- | --- | --- | --- |

---
<!-- hwf:end -->
```

- **三行状态**：直接取 STATE 顶部「当前阶段 / 下一动作 / 待用户事项」，`state-set` 改这三项时自动刷新 issue，所以每次阶段转换、出现或解除待用户事项都必须用 `state-set` 更新。每行限 150 字，只写一句结论。
- **勾选**：由脚本核对，步骤 JSON 里该步的 `commits` 全是对应项目 `release-<根编号>` 的祖先才打勾；汇总新提交后带 `--steps-file` 重跑。不得为了打勾虚报 commits。
- **步骤标题**：限 80 字，只写做什么；分支、MR、流水线、验收结果、证据一律写评论，不进描述。单步骤直达只写一项。
- 脚本写完自动回读，核对用户原文未变；失败就停下修，不手改描述兜底。

**跨仓库引用**：所有 issue/MR 描述、评论、进度、完整性核对、完成汇报与 ntfy，引用非当前项目的 MR/issue 必须用 `<仓库路径>!<编号>` / `<仓库路径>#<编号>` 或完整网址；裸 `!N` / `#N` 只用于同项目。回读逐个悬停或打开链接，核对项目路径与标题。

### 待定清单

根 issue 下只用一条评论，新增项编辑同一条，不另发/开单；免打扰下创建时机见 `communication.md`「通知模式」。STATE 记 note 链接。

```markdown
## 待定清单（只记录，用户点名才处理）
| # | 来自 | 问题 | 位置 | 影响 | 建议 | 状态 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 步骤 2 代码评审 | 卸载回调用例互相依赖 | tests/xx.spec.ts | 偶发误报 | 做 | 待定 |
```

状态只用：待定 / 已处理（附 SHA）/ 转为 #<新 issue>。

### 登记池

每仓库固定一张 `登记池：与需求无关的问题（只记录，不排期）`，`状态:等你处理`、长期 open。编号取 `docs/agents/herdr-project.yaml` 的 `gitlab.registry_issue`；未配置用 `glab issue list --search "登记池："` 查，仍没有先问用户，不自行新建。

```markdown
**<日期> · 来自 #<根编号> 的<阶段>**
- 现象：<一句话>
- 位置：<文件 / 页面 / 用例>
- 用户能不能感觉到：能 / 不能
```

重复问题在原评论回复「<日期> 在 #<根编号> 再次出现」，不重复登记，不派人处理；用户点名要做才开新根 issue。

### 标签允许列表

全部只有以下 9 个，不新增、不用已废弃旧标签。

| 组 | 标签 | 使用条件 |
| --- | --- | --- |
| 类型 | `需求` | 根 issue（spec、直达唯一 issue、收件箱发起并进入交付的根 issue） |
| 类型 | `子任务` | §3.1 子 issue |
| 进度 | `状态:等你处理` | 用户拍板、SQL、登录、合并授权、澄清、决定做不做；登记池 |
| 进度 | `状态:待开始` | 已排好，等派人 |
| 进度 | `状态:方案中` | 复杂度判定、写/评方案、写/评用例（交付根 issue 仅方案路径使用；接单对话按下文） |
| 进度 | `状态:开发中` | 开发、代码评审及回改 |
| 进度 | `状态:测试中` | 自动化测试、合 develop、冒烟 |
| 进度 | `状态:待上线` | 代码全进 release、main MR 已提，等用户合并；仅根 issue，子 issue 已关闭 |
| 开关 | `herdr-auto` | 收件箱开关，含义见 `communication.md`「GitLab 收件箱」 |

- open issue 恰好一个进度标签。转换用同一命令去旧加新，如 `glab issue update <iid> --unlabel "状态:开发中" --label "状态:测试中"`，回读只剩一个。社区版无互斥标签，由 scheduler 保证。
- 接单先回读并整理标签，用户只需 `herdr-auto` 与指派。对话模式不打 `需求`，分析时 `状态:方案中`、结论回复等用户时 `状态:等你处理`；明确开工（如 `/go`）且该单为根时补 `需求`、换当前阶段；另建根时发起 issue 不打 `需求`，跟随根阶段。
- 用户标签与实际不符或多个状态，直接改实际阶段，回读、记 STATE，不用问。不动 `herdr-auto`，不加允许列表以外标签。
- 每次转换先 STATE、再标签，INDEX 同步一句人话。等用户一律 `状态:等你处理`，答复后恢复原阶段。收件箱会按标签历史恢复并在转交消息说明；若回复仍需用户处理，scheduler 改回等待。
- 根标签跟当前最靠前的未完成步骤；全完成前不为待上线。关闭 issue 无需进度标签；子关闭表示代码进 release，根关闭表示上线或作废，作废评论说明原因。
- 需求看板编号取项目配置 `gitlab.board_id`，6 个状态列；给用户链接必须带 `?label_name[]=需求`，只看根需求：`https://<host>/<project>/-/boards/<board_id>?label_name[]=需求`。

## 文档最小化

步骤与子 issue 不写独立一次性报告（如 `REPORT.md`）；改动、命令、结果、未验证项和验收映射写 issue 完成评论及 commit message。

共用产物只在根需求维护：最终技术方案（仅方案路径）、决策记录、已评审用例、上线清单、`reviews/` 评审结论。步骤不重复产出同级文档，不为留档复制同一内容。
