# 代码评审与测试

代码看起来正确，不代表真实操作能通过。本主题规定先独立评审，再按已批准用例测试并交付真实证据；缺证不能当作通过。

进入 §7–8、测试回改或冒烟准备时读取。实现前放行与红绿证据见 `implementation.md` §6；发布顺序与关闭见 `delivery.md` §9。角色配置以 `../herdr/config.yaml` 为准；角色独立性、成员状态与派活见 `scheduling.md`，通知与截图评论时机见 `communication.md`「通知模式」。

## 7. code-review 代码评审与 arch 关键风险终审

完整代码评审累计最多 **6 轮**，切模型、会话和测试回改不清零。常规评审由 code-review 执行，precheck 整理相关检查和原始证据；独立性按 `scheduling.md`「双层评审与独立性」执行。

先检查真实 diff 与验收覆盖；仅为确认候选问题展开调用链、异常与状态路径、测试缺口。无关基线失败单独归因，不重跑全量套件，也不得把红灯记绿。

code-review 必须核对 `implementation.md` §6 的实现前放行记录，以及每次红/绿运行的 `run.json`、源码快照和原始输出：放行范围与实现一致，源码指纹匹配，`source_unchanged` 为 true，测试自身退出码与输出一致；单元测试先于对应实现，没有为过测弱化用例。缺证或未经批准改变通过标准即退回；合法用例更正须有独立复核记录与重新验证证据，当前全绿不能替代。

### 评审范围契约

所有代码评审适用：

- 范围是 `review-files.json` / 冻结 diff，以及确认候选问题必需的直接调用方、被调用方和相关测试。每个复核项对应一条验收标准或一个具体风险，不写开放式「完整检查整个链路」。
- 无关模块、既有基线失败、通用测试债务、无关重构、未要求的生产 GUI / PostgreSQL 验收只列 out-of-scope，不在本轮展开。
- 派活必须写预算，默认 20 分钟 / 30 次工具调用；大 diff 可上调但须写理由。超过 20 个文件或 100KB，必须拆成两段或明确上调。用到 70% 仍未收敛时先输出候选问题并停止扩展，由 scheduler 决定是否追加。
- 每条验收标准都有结论且无新阻断候选即停止；不重复读文件或核查同一问题来「确认」。发现阻断先报告，再决定是否查下一项。
- 阻断 / 高风险影响结论；建议、验证缺口、out-of-scope 单列，不扩范围。非严重项按 `planning.md`「issue 数量与进度标签」记入根 issue 待定清单，无关发现记入登记池。
- 回改只核验 `上次已审版本..当前版本` 增量及受影响调用链；仅触发下述升级条件时重开完整评审。

### 风险终审与回改

1. **arch 入口**：常规问题已闭环，相关检查有真实结果，未验证项与剩余风险明确后才提交最终版本。交接包含基准/当前 SHA、原始 diff 入口、一页以内的不变量与验收摘要、问题 ID/状态/关闭证据、风险与未决项。默认全新短会话，不带历史聊天；arch 可直接查源码与证据，不只批准摘要。
2. **arch 职责**：独立判断关键架构与跨模块契约、并发状态和数据一致性、安全权限、不可逆迁移/回滚、严重争议，签发最终风险结论。不重复常规查找、lint、测试或逐条非严重回改核验。默认一次集中终审是调度策略，不是最多两轮限制。
3. **普通回改**：交 code-review 按问题 ID、验收条件、已审 SHA 核验增量和受影响调用链，不只看改动行。实现者不能自报关闭；证据不足、严重问题未消除、测试版本与交付版本不一致，一律不放行。
4. **升级条件**：推翻 arch 关键判断，改变核心契约/安全边界/关键不变量，扩散到未覆盖的重要模块，严重争议未解，修复证据冲突；或测试/冒烟失败后的回改碰到 `planning.md` §0 关键决定、方案取舍、验收口径。code-review 每次回改结论必须写「是否碰到关键决定/方案取舍/验收口径：是/否 + 依据」；写「是」或写不出依据，scheduler 必须交 arch。交接仅含问题状态、增量 diff、相关证据，必要时扩大到受影响模块，不默认重审全部历史。
5. **最终放行**：已有 arch 风险终审通过，其后增量经独立 code-review 核验无未解决严重问题、未触发升级，相关验证对应最终交付版本；触发升级先取新的 arch 裁决。STATE 分别记录最终 arch 已审 SHA、code-review 已审 SHA、两者增量与不升级依据。
6. **轮数与成本**：为必要风险终审预留轮次；未获 arch 放行，不能拿 code-review 最后一轮常规通过充当最终通过。记录 arch 调用原因、完整评审/定点核验类型、实际 model/thinking、全模型成本、严重漏检与返工；成本份额不是节省率。

严重问题按影响判断，不只凭 P0/P1：核心验收不满足、数据丢失、越权、安全漏洞、把失败判通过、改变未授权生产语义、不可回滚破坏、阻塞全部后续验证。审美、命名、低风险整理、可延后优化属于非严重项。

非严重项逐条记录来源步骤、代码位置、影响、建议后继续自动化测试，不新建跟踪 issue；交付末尾交用户挑选，点名才处理。**第 6 轮后不开第 7 轮**：仍有严重问题，由 arch 给出明确修复决定；修复后仅定点核验对应严重问题，保留计数。客观未消除就报告阻塞，不能因预算或轮数耗尽强行放行。

## 8. 代码评审通过后执行自动化测试

`test` 对实际 HEAD 执行 `implementation.md` §4–§5.1 开发前编写、评审、上传的用例；直达与 spec 路径均适用。步骤/子 issue 复用根需求已批准用例和 test-writer 补的定向断言，不另设用例评审轮次；防风险为「要」时加兼容场景。写用例与执行测试不共用会话，不按实现结果临时改通过标准。

### 测试范围与会话

- 用户明确启动完整交付流程即授权本阶段自动化测试，scheduler 记录授权与范围；普通咨询或只写方案不自动授权启动服务。
- 浏览器与 Electron 测试统一由 test 执行，工具/模型取 `../herdr/config.yaml`。普通网页使用仓库网页启动命令；仅涉及主进程、preload、安装更新、其他原生能力或需求明确要求时启动 Electron。两边涉及则分别覆盖并列结果，STATE 记录范围与启动方式理由。
- 每次测试（含复测）新会话，派活附上次报告路径和失败点；同一轮等待用户答复可继续原会话。
- 只运行本 issue 直接相关的文件、目录、用例。报告含命令、环境、HEAD、验收条目映射、截图/日志/报告路径和清理结果。
- 前后端都改时，后端按接口约定逐条验证；前端真实浏览器测试必须等后端改动在 develop 部署成功，连真实后端，不用模拟接口。开发并行安排见 `scheduling.md`「前后端并行开发」。

### 准备与预检

每轮（含复测）先用不超过 10 分钟预检，报告开头写每项结论与耗时：

1. HEAD 与派活一致，本 issue 专属服务按「独立服务与每轮清理」启动。
2. 按下述脚本准备浏览器，能打开被测页面并截到真实截图。
3. 页面正常渲染，账号可登录且权限、积分足够，真实用户操作能到功能入口，依赖接口已部署且无未部署/鉴权错误。
4. 逐条列出验收点所需前置状态与造法。

服务启动后运行：

```bash
python3 ~/.hwf/scripts/test-browser.py <本 issue worktree> --url <被测地址> --account <测试账号> --out <本轮证据目录>
```

脚本每次重建 `<证据目录>/browser-profile` 并调用项目登录脚本，成功输出一行 JSON。Codex 用可用浏览器工具按 `open.app.path`、`open.app.args`、`url` 打开同一 profile，保留登录状态；`open` 是 omp 参数格式，不是 Codex 工具名。脚本建立的目录就是干净环境，不另查 localStorage、不换目录、不用共用目录。`"ok": false` 按 `stage` 处理；项目未配登录脚本则在页面登录。

浏览器目录、登录、遮罩/弹窗、占用端口、页面入口、测试造数由 test 自行处理：先读已知做法笔记，再换办法，同一问题最多换 2 种办法，仍失败才标阻塞并报告每种办法与现场。只有代码缺陷、账号/积分/权限不足、后端未部署或接口报未部署、测试工具本身不可用才直接停下回报。

处理后预检第 1–3 项任一仍不成立，或全部验收点无法造条件，立即停止，不跑验收点；按清理规则关闭服务，以 `阻塞` 结尾，附对应预检项、报错原文、现场截图、已试办法。部分验收点无法造条件则逐点标阻塞，其余继续；正式测试某点造条件连续失败 2 次，同样跳到下一点。

scheduler 按原因分派，原因未变不得原样重派：代码交 dev 并走回改路径；工具/环境先让 test 换可用办法，换执行体或需用户动手时按 `communication.md` 通知；账号/权限/积分/未部署交用户或负责人；造不出条件问 dev 或 arch。预检失败不是免测，浏览器与截图门禁仍未满足，不得关单。

### 测试知识与数据

- 每任务一份 `<任务目录>/test/howto.md`。test 开测前读，收尾前补已确认有效的登录、入口、造数方式（含可复用 ID）、坑与解法；失效内容直接改，不写流水账。派活只附路径。
- 每项目一份 `<主仓库>/.hwf/test-data.md`，不入库；主仓库为 `git rev-parse --git-common-dir` 的上一级。按环境、账号记录可长期复用数据的类型、ID、查找方式、自检办法、来源任务、最后确认日期。造数前先查并自检，可用就复用，没有才造；补入新可复用数据，修正或删除失效行。不记密码/token，不破坏或删除清单数据，必须改动则测完恢复。文件不存在由 test 新建。

### 浏览器、UI 与截图门禁

- 遵守仓库 `AGENTS.md` 的 develop 环境、端口、登录、真实用户导航和截图要求；不抢同一登录会话。
- 所有前端相关修改（含仅测试、fixture、样式、构建配置、相关文档）都必须真实浏览器自动化。只有用户对本任务明确说不需要才可豁免，STATE 保存原话与范围，并在交付披露。调度者、作者、评审者不能以低风险、仅文档/测试、未改生产行为、成本或已过审方案自行豁免；Node/jsdom、单元/组件测试不替代。
- 涉及 UI/页面/组件/样式，逐项走查布局与视觉。有设计稿则颜色、字体、字号、间距、圆角、层级、文案一致；宽高依内容与容器处理，不照抄固定数值或写死尺寸。无设计稿至少对齐、间距、换行、溢出正常，无重叠、错位、截断、异常空白。偏差退 dev 修复复测，结论与截图进报告。
- 每个前端关键场景都提供真实运行截图与通过/失败/阻塞结论；失败、受阻也留现场。无法运行或截图就记录阻塞与缺证，保持未完成，不改成不适用。
- **截图交付门禁**：逐点上传真实截图到当前任务 tracker，在对应 issue 评论用图片 Markdown 内嵌，标环境、SHA、结果；免打扰时依 `communication.md`「通知模式」放进步骤完成汇总。保留旧失败截图与记录，不覆盖或改绿。回读评论和上传链接确认可访问才算交付；本地路径或仅附报告不替代。无访问/上传能力即阻塞。

### 独立服务与每轮清理

本节是测试服务启动与每轮清理的权威规则；交付级目录和资源保留判据见 `worktrees.md`。

- 每个 issue 的每轮自动化测试/冒烟必须新启动专属服务，不复用本 worktree 先前 issue、其他成员、用户或其他任何已运行服务。先查端口归属，非本 issue 占用则依仓库规则另选空闲端口，记录端口、origin、进程标识、启动时间；无法保证 origin 隔离即阻塞，不复用或停止对方服务。
- 服务以本 issue worktree 为 cwd；确需别处启动，报告 PID，收尾按 PID 关闭并回读端口。
- 派活必须写独立启动、关闭、端口回读要求。test 每轮回报前关闭本 issue 新启动服务及全部后台进程，回读所有用过端口空闲；只关本 issue 进程。报告记录启动/关闭动作、端口结果、残留进程。
- 统一执行 `python3 ~/.hwf/scripts/stop-test-services.py <本 issue worktree> --port <本 issue 用过的端口>`，退出码 0 才算完成，输出原文进报告。脚本按 worktree 内 cwd 且监听端口认领整棵服务树（含 `pnpm exec` 包装进程），不碰 agent 或其他 worktree。只关 pane / Ctrl-C 不够，后台和 omp 命名服务可能残留；omp 命名服务另用 `write proc://<名称>/kill` 清掉其记录。
- 自己启动的浏览器也每轮关闭；同轮复用一个，不每个验收点重开。浏览器以本 issue worktree 为 cwd，调试端口让脚本识别。报告写「本轮打开 N 个浏览器，已全部关闭」并附脚本输出。
- 删除本轮 `<证据目录>/browser-profile`（含登录凭据），报告确认已删。
- scheduler 派活只给测试内容、按 `scheduling.md`「多调度者并行」领取的账号、地址，不指定浏览器路径、profile、`persist` 等参数。scheduler 和 arch 不另加干净环境检查或环境停止条件，环境要求只由 `test-browser.py` 和本节承担。

### 测试失败后的回改

失败交 dev 修复 → 独立 code-review 核验增量 → test 复测。只有触发 §7「风险终审与回改」升级条件才再交 arch；完整评审计数不清零，达上限仅走严重项定点核验，最终版本仍须满足 §7 放行条件。
