# 代码评审与测试

代码看起来正确，不代表真实操作能通过。本主题规定先独立评审，再按已批准用例测试并交付真实证据；缺证不能当作通过。

进入 §7–8、测试回改或冒烟准备时读取。实现前放行与红绿证据见 `implementation.md` §6；发布顺序与关闭见 `delivery.md` §9。角色配置以 `../herdr/config.yaml` 为准；角色独立性、成员状态与派活见 `scheduling.md`，通知与测试证据评论时机见 `communication.md`「通知模式」。

## 7. code-review 代码评审与 arch 关键风险终审

本阶段常规评审与回改核验统一计轮，累计最多 **3 轮**（第 1 轮首次常规评审 + 最多 **2 轮**回改核验）；切模型、换会话或中途触发升级交 arch 裁定均**不清零、不增加轮次**，也不得把回改核验记作“不占轮数的定点复核”绕过上限。常规评审由 code-review 执行，precheck 整理相关检查和原始证据；独立性按 `scheduling.md`「双层评审与独立性」执行。

进入本节派发 `precheck` / `code-review` 前，先对冻结 diff 执行 `python3 ~/.hwf/scripts/semantic-lint.py --repo <本 issue worktree> --base <基准分支> --json` 团队铁律语义预检：退出码 `2`（命中灰度开关、硬编码密钥、远端执行命令或 `main` 自动合并等红线）时直接退回 `dev` 自修，**不计入本节 3 轮评审上限**；退出码 `0` 时将 `advisory` 候选（若有）随派活单供 `precheck` / `code-review` 定向核对源码，`skipped`（如离线）时照常推进不阻塞。

code-review 按 skill `scoped-code-review` 执行常规评审与回改核验，核对 `implementation.md` §6 的实现前记录与每次红/绿证据；缺证或未经批准改变通过标准即退回，当前全绿不能替代。生产实现已满足验收且红绿证据有效时，不得为源码中不存在的假想反例、内部异步拦截点位置、调用次数、内部 DOM 结构或多重极端时序巧合退回单测补断言、重跑留证；第 1 轮评审须一次列全可见阻断项。

### 评审范围契约

所有代码评审适用。范围、out-of-scope、默认预算（20 分钟 / 30 次工具调用）、70% 预算处理、停止条件与严重度分级以 skill `scoped-code-review` 为准。

- scheduler 派活必须写 in-scope/out-of-scope、复核项、预算和停止条件；每个复核项对应一条验收标准或一个具体风险。大 diff 上调预算须写理由，超过 20 个文件或 100KB 必须拆成两段或明确上调；评审者用到 70% 预算先交候选问题，由 scheduler 决定是否追加。
- 非严重项按 `planning.md`「issue 数量与进度标签」记入根 issue 待定清单，无关发现记入登记池。
- 回改核验只核上次未过项是否关闭、本次增量是否在正常或验收场景引入必现/高概率回归，以及本轮红绿证据是否有效；不顺调用链外推低概率极端假设。

### 风险终审与回改

1. **arch 入口**：常规问题已闭环，相关检查有真实结果，未验证项与剩余风险明确后才提交最终版本。交接包含基准/当前 SHA、原始 diff 入口、一页以内的不变量与验收摘要、问题 ID/状态/关闭证据、风险与未决项。默认全新短会话，不带历史聊天；arch 可直接查源码与证据，不只批准摘要。
2. **arch 职责与边界**：独立判断关键架构与跨模块契约、并发状态和数据一致性、安全权限、不可逆迁移/回滚、严重争议，签发最终风险结论。**arch 只给业务契约、安全不变量、允许修改的文件边界与回滚/上线要求，禁止编写具体单元测试用例、夹具构造步骤、内部拦截点位置或调用次数清单**；也不重复常规查找、lint、测试或逐条非严重回改核验。
3. **普通回改（单趟闭环）**：同一轮的全部需修改项按 `implementation.md` §6「回改打包」一次交 dev 在单趟内完成回改前红证、代码修改与绿证，再交 code-review 按 skill `scoped-code-review`「回改核验」一次核验红绿证据与代码增量。实现者不能自报关闭；证据不足、严重问题未消除、测试版本与交付版本不一致，一律不放行。
4. **升级条件**：推翻 arch 关键判断，改变核心契约/安全边界/关键不变量，扩散到未覆盖的重要模块，严重争议未解，修复证据冲突；或测试/冒烟失败后的回改碰到 `planning.md` §0 关键决定、方案取舍、验收口径。code-review 每次回改结论必须写「是否碰到关键决定/方案取舍/验收口径：是/否 + 依据」；仅在方案取舍或既有关键决定本身需要变更/补充裁决时才写「是」交 arch（按既有裁定修局部遗漏写「否」，不反复升级），且升级不重置本阶段评审轮次。交接仅含问题状态、增量 diff、相关证据。
5. **最终放行与终审轮限**：arch 风险终审最多 **2 轮**。若第 1 轮判 `需修改`，dev 按单趟闭环修复留证 → code-review 仅核对 arch 点名风险项（最多 2 轮，不借机重开常规挑刺）→ arch 只复核上次未过项；第 2 轮仍不通过则整理分歧与选项交用户裁定，不开第 3 轮。已有 arch 风险终审通过后，其后测试/集成回改增量经独立 code-review 核验无未解决严重问题且未触发升级，相关验证对应最终交付版本即可放行；触发升级先取一次 arch 裁决。STATE 分别记录最终 arch 已审 SHA、code-review 已审 SHA、两者增量与不升级依据。
6. **轮数与成本**：未获 arch 放行，不能拿 code-review 最后一轮常规通过充当最终通过。记录 arch 调用原因、完整评审/回改核验轮次、实际 model/thinking、全模型成本、严重漏检与返工；成本份额不是节省率。

严重与非严重的口径见 skill `scoped-code-review`「严重与非严重」。非严重项逐条记录来源步骤、代码位置、影响、建议后继续自动化测试，不新建跟踪 issue；交付末尾交用户挑选，点名才处理。**第 3 轮（第 2 次回改核验）后不开第 4 轮审查**：非严重或极端理论巧合项记入待定清单直接放行；确属正常路径必现/高概率的验收失败或数据损坏，由 arch 给出**唯一一次最终收口改法**（只定目标文件改法与底线，不列单测细则），dev 单趟修完并留红绿证后，code-review **仅核对 arch 点名项是否按裁定落实，严禁再顺藤摸瓜提出任何新阻断**——落实即进入风险终审（或同轮由 arch 签发），客观未消除就报告阻塞交用户决定，不能强行放行。

## 8. 自动化测试（正常流程代码评审后，debug 部署后）

正常流程中，`test` 对实际代码版本执行 `implementation.md` §4–§5.1 开发前编写、评审、上传的用例；直达与 spec 路径均适用。步骤/子 issue 复用根需求已批准用例和 test-writer 补的定向断言，不另设用例评审轮次；防风险为「要」时加兼容场景。写用例与执行测试不共用会话，不按实现结果临时改通过标准。debug 按下节的 issue 验收与部署版本执行。

测试环境范围全流程统一读取 `docs/agents/herdr-project.yaml` 的 `smoke`：**默认只测 `default` 不为 `false` 的地址（如国内 `develop`）**。`default: false` 的地址（如国际/海外站）仅在用户明确要求测该站点，或本次改动专门修改了该站点独有配置/分支逻辑时才纳入本节验收与账号预检；普通共用组件、通用展示或多语言词条常规同步不触发 `default: false` 站点实测，预检不因缺该站点账号报阻塞，scheduler 也**不得停下请用户决定是否免测该站点**，直接在报告注明「<名称>未验（默认不验）」。UI 走查深度按 skill `real-browser-acceptance` 匹配改动大小：纯局部显隐/文案/单行样式微调只核对真实目标界面与基本入口，不额外注入大批量虚构数据跑多视口滚动或重测无关确认框。

正常流程按风险与形态分两种执行方式：

- **单分支低风险直达合并冒烟**：同时满足「直达路径、`防风险 = 不要`、单仓库单开发分支、项目已配置 `branches.test` 与可用默认 `smoke` 地址、不涉及主进程/preload/安装更新等桌面原生能力」时，`§7`（含 `arch` 风险终审）通过后不再先起本地 Web 服务跑第一遍，直接按 `delivery.md`「合并顺序与版本一致性」将已审开发分支合入 `develop` 并等待部署成功，由 `test` 在默认 `smoke` 地址一次性跑完 `§4–§5.1` 已批准的全部用例、UI 走查与录屏/截图证据上传，同时满足本节自动化验收与 `delivery.md` §9 测试环境冒烟。
- **本地独立服务验收 + 测试环境冒烟**：`方案路径`、`防风险 = 要`、涉及桌面原生能力、多仓库/多分支，或项目未配置测试分支/默认 `smoke` 地址（及测试环境暂不可用经用户同意先测本地）时，先在本 issue worktree 新启动专属服务完成本节验收，通过后再合入 `develop` 执行测试环境冒烟。

### debug：部署后验收

debug（含 §0 转入的极简路径）只在 develop 部署成功后执行本节真实验收，顺序与授权以 `implementation.md`「debug 模式」为准。它不要求 §7 代码评审/arch 放行、§4–§5.1 用例评审或 snippet；验收依据是 issue 的用户要求（§0 转入时含理解卡验收条件），不能按实现结果临时降低标准。

- scheduler 派 `test` 新会话，附验收点、干净开发分支 SHA、develop MR/部署 SHA/成功部署作业、项目默认 `smoke` 地址及对应账号；每轮重新核对实际部署版本包含本次代码。前后端都改时分别核对相关部署，不能只凭合并成功开测。
- 普通网页在 `smoke` 地址用真实浏览器逐点操作，真实请求连接测试环境；后端改动按接口验收，存在页面操作链路时一并覆盖。涉及主进程、preload、安装更新等桌面原生能力，用包含本次改动且连接 develop 的测试客户端，记录测试包版本、构建 SHA、来源和连接环境。网页通过不能替代桌面原生验收。
- 不启动本地 Web 服务、开发版 Electron 或用本地页面做端到端验收。缺测试分支/地址、部署失败、测试客户端不可用或无法确认版本/环境时直接报阻塞和恢复动作；不转本地、不自行跳过。此限制不影响 §6 的本地单元测试、lint 与 type-check。
- test 按 skill `real-browser-acceptance` 的「部署后验收」执行，复用下文预检、数据、取证门禁与清理要求；需 arch 决定的歧义由 scheduler 问用户，不引入完整流程。
- 每轮仅关闭本任务启动的本机浏览器、测试客户端和辅助进程，清理本轮凭据 profile，记录本地端口与清理结果；本机进程按下文清理脚本核验。远端 develop 服务以及他人客户端不属于本任务，禁止关闭。下文独立本地服务启动要求不适用于 debug；正常流程不因本例外改变。
- 失败走 `implementation.md`「debug 模式」的单趟红绿留证与修复 → code-review 核验红绿证据（最多 2 轮）→ 重新部署 → 新 test 会话复测，不走本文件 §7 的整项评审/arch 升级链。通过报告须逐条包含结果、真实证据、部署版本及客户端版本（有则），全部通过才交 scheduler 创建 release MR。

### 测试范围与会话

- 用户明确启动完整交付流程即授权本阶段自动化测试，scheduler 记录授权与范围；普通咨询或只写方案不自动授权启动服务。
- 浏览器与 Electron 测试统一由 test 执行，工具/模型取 `../herdr/config.yaml`。普通网页使用仓库网页启动命令；仅涉及主进程、preload、安装更新、其他原生能力或需求明确要求时启动 Electron。需要本地 Electron 验收时，直接在本 issue worktree 启动开发版 Electron（受固定端口如 `3001` 约束时先核实端口空闲），用 Computer Use 操作该窗口并在本轮收尾关闭，除非验收安装/自动更新产物本身，否则不索要签名安装包、也不为“能否启动本地 Electron”请示用户。两边涉及则分别覆盖并列结果，STATE 记录范围与启动方式理由。
- 每次测试（含复测）新会话，派活附上次报告路径和失败点；同一轮等待用户答复可继续原会话。
- 只运行本 issue 直接相关的文件、目录、用例。报告含命令、环境、HEAD、验收条目映射、录屏（含时间段）/补充截图/日志/报告路径和清理结果。
- 前后端都改时，后端按接口约定逐条验证；前端真实浏览器测试必须等后端改动在 develop 部署成功，连真实后端，不用模拟接口。开发并行安排见 `scheduling.md`「前后端并行开发」。

### 准备与预检

test 每轮（含复测）先预检，不超过 10 分钟，报告开头写每项结论与耗时。工具由执行者按当前全局规则选择。浏览器目录、登录、遮罩/弹窗、端口、页面入口、测试造数由 test 自行处理，同一问题最多换 2 种办法：登录时优先按 skill `real-browser-acceptance` 从本机测试账号清单读取本轮分配账号的凭据自行输入登录（网页用 Ego Lite、Electron 窗口用 Computer Use，录屏避开凭据文件与输密过程），**严禁未经自动登录尝试就停在登录页请用户手动登录，也严禁因自动化输入过测试账号密码而要求用户轮换测试账号密码**；非生产测试站点带入其他账号登录态时，核对同站点并发后仅清理该测试站点登录态并切换为本轮账号，不得向用户索要空白浏览器资料或 `profileId`（仅同共享测试域名正被其他在途任务使用时排队等待）。只有代码缺陷、账号/积分/权限不足、真人专属验证码/鉴权无法自理、后端未部署或接口报未部署、测试工具本身不可用才直接停下回报。预检第 1–3 项仍不成立或全部验收点无法造条件时，不跑验收点，清理后以 `阻塞` 结尾。

**仅当触发真人专属验证码/硬件鉴权、无可用测试账号凭据或自动登录排障后仍失败，确需用户亲自登录时，窗口就绪才是交接点。** test 确认登录页可见并可由用户接手后，保持该窗口与会话，立即向 scheduler 返回本轮结论：「登录窗口已就绪｜窗口名称与页面｜需人工原因｜请在此窗口登录，登录后回『已登录』」，结尾单列「阻塞」。不等预检超时，不轮询登录，不先清理窗口，也不等其他验收做完才报。本机测试账号可自动完成的正常登录不触发此交接。

scheduler 收到后立即按 `communication.md` 的用户待办流程转告并通知；此前只说过「需要账号」不等于已告知「窗口已就绪」。只请用户在页面操作，不索取密码或验证码。用户确认后，test 在原会话核实登录状态再续测；实际收尾时清理。

scheduler 按原因分派，原因未变不得原样重派：代码交 dev 并走回改路径；工具/环境先让 test 换可用办法，换执行体或需用户动手时按 `communication.md` 通知；账号/权限/积分/未部署交用户或负责人；造不出条件问 dev 或 arch。预检失败不是免测，浏览器与真实运行取证门禁仍未满足，不得关单。

### 测试知识与数据

每任务一份 `<任务目录>/test/howto.md`，每项目一份 `<主仓库>/.hwf/test-data.md`（不入库）。test 开测前读、收尾前补，写法与数据保护要求见 skill `real-browser-acceptance`「补经验」；派活只附 howto 路径。

### 浏览器、UI 与取证门禁

- 所有前端相关修改（含仅测试、fixture、样式、构建配置、相关文档）都必须真实浏览器（或 Electron 窗口）自动化。只有用户对本任务明确说不需要才可豁免，STATE 保存原话与范围，并在交付披露。调度者、作者、评审者不能以低风险、仅文档/测试、未改生产行为、成本或已过审方案自行豁免；Node/jsdom、单元/组件测试不替代。
- scheduler 核对本轮实际操作与验收点是否对应；执行者更换工具时，应有对应步骤的原因和现场。缺证的点保留原结果、标「待验证」，只退回该点补验。
- 涉及 UI/页面/组件/样式，按 skill 逐项做 UI 走查，偏差退 dev 修复复测，结论与录屏/截图证据进报告。
- 前端与客户端真机验收必须按验收标准编号成段保存「操作前状态 → 关键操作 → 可观测结果」的完整过程录屏（`.mp4`，命名与合录规则见 skill `real-browser-acceptance`），逐条标注起止时间段与通过/失败/阻塞结论，避免把同一条冒烟按每次点击切成零碎短片；失败、受阻也留现场。**已录制有效 `.mp4` 的验收点必须上传并交付视频，严禁弃用已录视频退回只贴静态截图**。仅客观无法录屏、录屏不可回放或静态细节在视频中看不清时，写明具体原因并用同轮截图补足；两者都无法取得就记录阻塞与缺证，保持未完成，不改成不适用。
- **界面与文案回改作废旧录屏**：测试回改或用户中途反馈修改了界面布局、按钮位置、样式或可见文案时，受影响验收条目的改前录屏自动作废（仅保留作历史记录），必须基于改后代码重新录制最新画面后才可判通过；只补改后静态截图或沿用改前旧录屏充数一律按缺证退回（涉及一次性绑卡/扣款等外部副作用无法在测试环境重跑全链路时，按 skill 在真实浏览器挂载同版本已审真实组件夹具补录完整交互过程并如实注明模拟边界）。
- **证据交付门禁**：test 按 skill 用 `scripts/upload-media.py create` 静默上传本轮录屏（及必要的补充截图），在报告中按验收标准逐行给出 `markdown`（`![说明](/uploads/...)`）、起止时间段与 `web_url`（`https://<host>/-/project/<数字项目ID>/uploads/...`），不直接发 issue 评论；scheduler 用 `upload-media.py check` 逐个核验可访问后，在步骤或整项完成评论的 `<details>` 折叠区**之外**按 `delivery.md` §9 直接贴出「验收标准逐条对账表」，每行同时原样内嵌播放器 `markdown`（不得包进代码块/反引号）、起止时间段与 `web_url` 裸直链（供飞书点击打开，**严禁手拼 `/<namespace>/<project>/uploads/...` 导致 404**，也**严禁只挑几段代表视频或把证据全藏进折叠长文**），并注明环境与 SHA。保留旧失败录屏/截图与记录，回读评论和上传链接可访问才算交付；本地路径、裸 `.mov` 或仅附报告不替代。无访问/上传能力即阻塞。

### 独立服务与每轮清理

本节是测试服务启动与每轮清理的门禁，操作见 skill `real-browser-acceptance`「启动专属服务」「每轮清理」；交付级目录和资源保留判据见 `worktrees.md`。

- 需要本地验收的每轮测试必须在本 issue worktree 新启动专属服务，不复用本 worktree 先前 issue、其他成员、用户或其他任何已运行服务；无法保证 origin 隔离即阻塞。直接测已部署环境的轮次（单分支低风险直达合并冒烟、测试环境冒烟、debug）核对实际部署版本，不启动本地验收服务，远端服务不得关闭。
- 本地验收派活必须写独立启动、关闭、端口回读要求；test 每轮回报前执行 `python3 ~/.hwf/scripts/stop-test-services.py <本 issue worktree> --port <本 issue 用过的端口>`，退出码 0 才算完成，输出原文进报告，只关本 issue 进程。部署后验收轮次仅清理本任务本机浏览器、测试客户端和辅助进程，并回读本轮用过的本地端口。
- 按 skill「每轮清理」结束本轮浏览器会话；仅在创建了独立 `browser-profile` 时要求删除并确认。
- scheduler 派活只给测试内容、按 `scheduling.md`「多调度者并行」领取的账号和地址，不指定测试工具和启动参数。scheduler 和 arch 不另加环境停止条件。

### 测试失败后的回改

正常流程：test 一轮跑完全部能跑的验收点再交接（缺陷挡住后续点时如实记阻塞）。只要既有 `§0` 关键决定与用户已确认验收口径本身无需变更，scheduler 直接按 `implementation.md` §6「回改打包」把本轮全部失败一次交 dev 在**单趟内**完成全链路排障、改前红证、修复与改后绿证 → 独立 code-review 核验增量与红绿证据 → test 复测：
- **禁止拆碎只读接力与重复打扰用户**：不得在派 dev 修复前拆成「dev 只读定位 → 只写单测不改生产 → arch 只读核证 → test 定点采帧」等多道只读工序，也不得在验收产品语义未变时停下请用户重新确认改法。
- **全链路复现与联动修复（禁止单文件挤牙膏）**：dev 必须沿触发入口到最终可观测结果的完整运行调用链（如状态观察 → 门控 → 执行器 → 网络请求/持久化/界面呈现）构造端到端 `--phase red` 复现，并在本需求授权边界内一次修齐该调用链上的全部耦合文件；上下游状态或门控耦合时，scheduler 与 arch **不得**人为把可写范围锁死在单个文件而漏掉下游链路。

单轮真机测试失败后的回改期，code-review 回改核验累计**最多 2 轮**（期间仅在方案取舍/关键决定本身需变更时才升级 arch，最多升级 1 次且不重置该 2 轮计数）。第 2 轮回改核验仍未通过时，按 §7 触顶规则处理：极端理论项记待定放行复测；真实严重项交 arch 给出唯一一次最终收口改法，dev 单趟修完后 code-review **仅核对点名项是否落实，严禁新增阻断项**，落实并满足 §7 最终放行条件即交 test 复测，仍未消除则报阻塞交用户决定。debug 仅按上方「debug：部署后验收」回改，不引入 arch 升级链。
