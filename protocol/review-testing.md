# 代码评审与测试

代码看起来正确，不代表真实操作能通过。本主题规定先独立评审，再按已批准用例测试并交付真实证据；缺证不能当作通过。

进入 §7–8、测试回改或冒烟准备时读取。实现前放行与红绿证据见 `implementation.md` §6；发布顺序与关闭见 `delivery.md` §9。角色配置以 `../herdr/config.yaml` 为准；角色独立性、成员状态与派活见 `scheduling.md`，通知与截图评论时机见 `communication.md`「通知模式」。

## 7. code-review 代码评审与 arch 关键风险终审

完整代码评审累计最多 **6 轮**，切模型、会话和测试回改不清零。常规评审由 code-review 执行，precheck 整理相关检查和原始证据；独立性按 `scheduling.md`「双层评审与独立性」执行。

code-review 按 skill `scoped-code-review` 执行常规评审与回改核验，其中必须核对 `implementation.md` §6 的实现前放行记录与每次红/绿证据；缺证或未经批准改变通过标准即退回，当前全绿不能替代。

### 评审范围契约

所有代码评审适用。范围、out-of-scope、默认预算（20 分钟 / 30 次工具调用）、70% 预算处理、停止条件与严重度分级以 skill `scoped-code-review` 为准。

- scheduler 派活必须写 in-scope/out-of-scope、复核项、预算和停止条件；每个复核项对应一条验收标准或一个具体风险。大 diff 上调预算须写理由，超过 20 个文件或 100KB 必须拆成两段或明确上调；评审者用到 70% 预算先交候选问题，由 scheduler 决定是否追加。
- 非严重项按 `planning.md`「issue 数量与进度标签」记入根 issue 待定清单，无关发现记入登记池。
- 回改只核验 `上次已审版本..当前版本` 增量及受影响调用链；仅触发下述升级条件时重开完整评审。

### 风险终审与回改

1. **arch 入口**：常规问题已闭环，相关检查有真实结果，未验证项与剩余风险明确后才提交最终版本。交接包含基准/当前 SHA、原始 diff 入口、一页以内的不变量与验收摘要、问题 ID/状态/关闭证据、风险与未决项。默认全新短会话，不带历史聊天；arch 可直接查源码与证据，不只批准摘要。
2. **arch 职责**：独立判断关键架构与跨模块契约、并发状态和数据一致性、安全权限、不可逆迁移/回滚、严重争议，签发最终风险结论。不重复常规查找、lint、测试或逐条非严重回改核验。默认一次集中终审是调度策略，不是最多两轮限制。
3. **普通回改**：交 code-review 按 skill `scoped-code-review`「回改核验」核验增量和受影响调用链。实现者不能自报关闭；证据不足、严重问题未消除、测试版本与交付版本不一致，一律不放行。
4. **升级条件**：推翻 arch 关键判断，改变核心契约/安全边界/关键不变量，扩散到未覆盖的重要模块，严重争议未解，修复证据冲突；或测试/冒烟失败后的回改碰到 `planning.md` §0 关键决定、方案取舍、验收口径。code-review 每次回改结论必须写「是否碰到关键决定/方案取舍/验收口径：是/否 + 依据」；写「是」或写不出依据，scheduler 必须交 arch。交接仅含问题状态、增量 diff、相关证据，必要时扩大到受影响模块，不默认重审全部历史。
5. **最终放行**：已有 arch 风险终审通过，其后增量经独立 code-review 核验无未解决严重问题、未触发升级，相关验证对应最终交付版本；触发升级先取新的 arch 裁决。STATE 分别记录最终 arch 已审 SHA、code-review 已审 SHA、两者增量与不升级依据。
6. **轮数与成本**：为必要风险终审预留轮次；未获 arch 放行，不能拿 code-review 最后一轮常规通过充当最终通过。记录 arch 调用原因、完整评审/定点核验类型、实际 model/thinking、全模型成本、严重漏检与返工；成本份额不是节省率。

严重与非严重的口径见 skill `scoped-code-review`「严重与非严重」。非严重项逐条记录来源步骤、代码位置、影响、建议后继续自动化测试，不新建跟踪 issue；交付末尾交用户挑选，点名才处理。**第 6 轮后不开第 7 轮**：仍有严重问题，由 arch 给出明确修复决定；修复后仅定点核验对应严重问题，保留计数。客观未消除就报告阻塞，不能因预算或轮数耗尽强行放行。

## 8. 自动化测试（正常流程代码评审后，debug 部署后）

正常流程中，`test` 对实际 HEAD 执行 `implementation.md` §4–§5.1 开发前编写、评审、上传的用例；直达与 spec 路径均适用。步骤/子 issue 复用根需求已批准用例和 test-writer 补的定向断言，不另设用例评审轮次；防风险为「要」时加兼容场景。写用例与执行测试不共用会话，不按实现结果临时改通过标准。debug 按下节的 issue 验收与部署版本执行。

### debug：部署后验收

debug 只在 develop 部署成功后执行本节真实验收，顺序与授权以 `implementation.md`「debug 模式」为准。它不要求 §7 代码评审/arch 放行、§4–§5.1 用例评审或 snippet；验收依据是 issue 的用户要求，不能按实现结果临时降低标准。

- scheduler 派 `test` 新会话，附验收点、干净开发分支 SHA、develop MR/部署 SHA/成功部署作业、项目 `smoke` 地址及账号；每轮重新核对实际部署版本包含本次代码。前后端都改时分别核对相关部署，不能只凭合并成功开测。
- 普通网页在 `smoke` 地址用真实浏览器逐点操作，真实请求连接测试环境；后端改动按接口验收，存在页面操作链路时一并覆盖。涉及主进程、preload、安装更新等桌面原生能力，用包含本次改动且连接 develop 的测试客户端，记录测试包版本、构建 SHA、来源和连接环境。网页通过不能替代桌面原生验收。
- 不启动本地 Web 服务、开发版 Electron 或用本地页面做端到端验收。缺测试分支/地址、部署失败、测试客户端不可用或无法确认版本/环境时直接报阻塞和恢复动作；不转本地、不自行跳过。此限制不影响 §6 的本地单元测试、lint 与 type-check。
- test 按 skill `real-browser-acceptance` 的「部署后验收」执行，复用下文预检、数据、截图门禁与清理要求；需 arch 决定的歧义由 scheduler 问用户，不引入完整流程。
- 每轮仅关闭本任务启动的本机浏览器、测试客户端和辅助进程，清理本轮凭据 profile，记录本地端口与清理结果；本机进程按下文清理脚本核验。远端 develop 服务以及他人客户端不属于本任务，禁止关闭。下文独立本地服务启动要求不适用于 debug；正常流程不因本例外改变。
- 失败走 `implementation.md`「debug 模式」的单测/实现前核验 → 修复 → 重新部署 → 新 test 会话复测，不走本文件 §7 的增量评审/arch 升级链。通过报告须逐条包含结果、真实证据、部署版本及客户端版本（有则），全部通过才交 scheduler 创建 release MR。

### 测试范围与会话

- 用户明确启动完整交付流程即授权本阶段自动化测试，scheduler 记录授权与范围；普通咨询或只写方案不自动授权启动服务。
- 浏览器与 Electron 测试统一由 test 执行，工具/模型取 `../herdr/config.yaml`。普通网页使用仓库网页启动命令；仅涉及主进程、preload、安装更新、其他原生能力或需求明确要求时启动 Electron。两边涉及则分别覆盖并列结果，STATE 记录范围与启动方式理由。
- 每次测试（含复测）新会话，派活附上次报告路径和失败点；同一轮等待用户答复可继续原会话。
- 只运行本 issue 直接相关的文件、目录、用例。报告含命令、环境、HEAD、验收条目映射、截图/日志/报告路径和清理结果。
- 前后端都改时，后端按接口约定逐条验证；前端真实浏览器测试必须等后端改动在 develop 部署成功，连真实后端，不用模拟接口。开发并行安排见 `scheduling.md`「前后端并行开发」。

### 准备与预检

test 每轮（含复测）先按 skill `real-browser-acceptance` 预检，不超过 10 分钟，报告开头写每项结论与耗时；浏览器统一用 `scripts/test-browser.py` 准备。浏览器目录、登录、遮罩/弹窗、端口、页面入口、测试造数由 test 自行处理，同一问题最多换 2 种办法；只有代码缺陷、账号/积分/权限不足、后端未部署或接口报未部署、测试工具本身不可用才直接停下回报。预检第 1–3 项仍不成立或全部验收点无法造条件时，不跑验收点，清理后以 `阻塞` 结尾。

scheduler 按原因分派，原因未变不得原样重派：代码交 dev 并走回改路径；工具/环境先让 test 换可用办法，换执行体或需用户动手时按 `communication.md` 通知；账号/权限/积分/未部署交用户或负责人；造不出条件问 dev 或 arch。预检失败不是免测，浏览器与截图门禁仍未满足，不得关单。

### 测试知识与数据

每任务一份 `<任务目录>/test/howto.md`，每项目一份 `<主仓库>/.hwf/test-data.md`（不入库）。test 开测前读、收尾前补，写法与数据保护要求见 skill `real-browser-acceptance`「补经验」；派活只附 howto 路径。

### 浏览器、UI 与截图门禁

- 所有前端相关修改（含仅测试、fixture、样式、构建配置、相关文档）都必须真实浏览器自动化。只有用户对本任务明确说不需要才可豁免，STATE 保存原话与范围，并在交付披露。调度者、作者、评审者不能以低风险、仅文档/测试、未改生产行为、成本或已过审方案自行豁免；Node/jsdom、单元/组件测试不替代。
- 涉及 UI/页面/组件/样式，按 skill 逐项做 UI 走查，偏差退 dev 修复复测，结论与截图进报告。
- 每个前端关键场景都提供真实运行截图与通过/失败/阻塞结论；失败、受阻也留现场。无法运行或截图就记录阻塞与缺证，保持未完成，不改成不适用。
- **截图交付门禁**：逐点上传真实截图到当前任务 tracker，在对应 issue 评论内嵌并标环境、SHA、结果；免打扰时依 `communication.md`「通知模式」放进步骤完成汇总。保留旧失败截图与记录，回读评论和上传链接可访问才算交付；本地路径或仅附报告不替代。无访问/上传能力即阻塞。

### 独立服务与每轮清理

本节是测试服务启动与每轮清理的门禁，操作见 skill `real-browser-acceptance`「启动专属服务」「每轮清理」；交付级目录和资源保留判据见 `worktrees.md`。

- 正常流程每个 issue 的每轮自动化测试/冒烟必须新启动专属服务，不复用本 worktree 先前 issue、其他成员、用户或其他任何已运行服务；无法保证 origin 隔离即阻塞。debug 例外：只用已部署的 develop 环境并核对部署版本，不要求也不允许启动本地验收服务，远端服务不得关闭。
- 正常流程派活必须写独立启动、关闭、端口回读要求。test 每轮回报前执行 `python3 ~/.hwf/scripts/stop-test-services.py <本 issue worktree> --port <本 issue 用过的端口>`，退出码 0 才算完成，输出原文进报告；只关本 issue 进程。debug 仅清理本任务本机浏览器、测试客户端和辅助进程。
- 自己启动的浏览器每轮关闭，报告写「本轮打开 N 个浏览器，已全部关闭」；删除本轮 `<证据目录>/browser-profile` 并在报告确认。
- scheduler 派活只给测试内容、按 `scheduling.md`「多调度者并行」领取的账号、地址，不指定浏览器路径、profile、`persist` 等参数。scheduler 和 arch 不另加干净环境检查或环境停止条件，环境要求只由 `test-browser.py`、本节和该 skill 承担。

### 测试失败后的回改

正常流程：失败交 dev 修复 → 独立 code-review 核验增量 → test 复测。只有触发 §7「风险终审与回改」升级条件才再交 arch；完整评审计数不清零，达上限仅走严重项定点核验，最终版本仍须满足 §7 放行条件。debug 仅按上方「debug：部署后验收」回改，不引入本链。
