# 验收测试用例

用例在开发前写好并评审，之后开发和测试都照它执行，不按实现结果临时改通过标准。用例要让另一个人不问作者也能照着跑、能判断通过还是失败。

## 编写步骤

1. **对齐依据**。逐条对照已确认的验收标准（有方案时同时对照已确认的方案或 spec），保留原验收编号。
2. **逐条写用例**。每条包含下表全部字段：

   | 字段 | 写什么 |
   | --- | --- |
   | 验收编号 | 对应的验收标准编号 |
   | 前置条件 | 账号、权限、数据、页面状态 |
   | 输入 / 操作 | 用户实际做的步骤，或接口请求 |
   | 预期结果 | 可观察的结果：界面、请求、数据 |
   | 失败判据 | 出现什么就算失败，堵住「看起来过了」 |
   | 数据准备 / 清理 | 怎么造、测完怎么恢复 |
   | 自动化方式 | 单元测试、接口测试或真实浏览器；对应的测试文件或目录 |
   | 证据要求 | 截图、日志、请求记录各要什么 |

3. **覆盖面**。主路径、边界、错误、回归，以及适用的权限和兼容性。涉及页面、组件、样式、布局时加 UI 走查：有设计稿对照视觉呈现，没有设计稿核对布局整齐。
4. **分清两类测试**：
   - 开发侧单元测试：写输入、预期输出、边界，开发先把它落实成可运行的测试（见 skill `test-first-evidence`）。
   - 最终自动化验收：写用户操作和可观察结果，代码评审通过后由测试人员在真实环境执行（见 skill `real-browser-acceptance`）。
5. **落盘**。用例文件用 `.md`，连同能提前写的自动化脚本一起落盘，写明运行命令和环境，只列直接相关的测试文件或目录，不写全量套件。

完成标准：每条验收标准至少有一条用例，每条用例的字段都填了，失败判据能区分真通过和假通过。

步骤或子 issue 继承根需求已评审的用例，只补必要的定向断言，不重写整份用例。

## 评审用例

逐条核对，结论写「通过」或「需修改」，并列出问题：

- **覆盖**：每条验收标准（有方案时含 spec）都有用例，没有漏掉错误、边界和回归。
- **假通过**：失败判据能否让错误实现失败；有没有永远会过的断言或 mock。
- **可复现**：前置条件、数据造法、操作步骤是否足够让别人照做。
- **清理安全**：造数和清理会不会破坏共用数据或别人的环境。

非严重的补充意见单独列出，不阻断开发；仍会假通过、无法验证或会破坏数据的缺口算严重，写明最小修正项。
