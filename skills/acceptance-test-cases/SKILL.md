# 验收测试用例

用例在开发前写好并评审，之后开发和测试都照它执行，不按实现结果临时改通过标准。用例要让另一个人不问作者也能照着跑、能判断通过还是失败。

## 编写步骤

1. **对齐依据**。逐条对照已确认的验收标准（有方案时同时对照已确认的方案或 spec），保留原验收编号。
2. **逐条写用例**。每条包含下表全部字段：

   | 字段 | 写什么 |
   | --- | --- |
   | 验收编号 | 对应的验收标准编号 |
   | 前置条件 | 账号、权限、数据、页面状态 |
   | 输入 / 操作 | 用户实际做的步骤，或接口请求 |
   | 预期结果 | 可观察的结果：界面、请求、数据 |
   | 失败判据 | 出现什么就算失败，堵住「看起来过了」 |
   | 数据准备 / 清理 | 怎么造、测完怎么恢复 |
   | 自动化方式 | 单元测试、接口测试或真实浏览器；对应的测试文件或目录 |
   | 证据要求 | 过程录屏（默认，注明起止动作与预期画面；仅静态细节看不清或任务指定时补截图）、日志、请求记录各要什么 |

3. **覆盖面与深度匹配改动大小**。覆盖主路径、边界、错误、回归及适用权限与兼容性，但不层层加码：
   - **环境范围**：读取项目 `docs/agents/herdr-project.yaml` 的 `smoke` 配置。`default: false` 的站点（如国际/海外站）在用户未明确点名、且本次未修改该站点独有配置/分支逻辑时，**不写进**端到端验收用例，也不要求双站点重复录屏/截图或双配置外层菜单重复挂载。
   - **走查深度**：新增页面/弹窗、修改滚动容器或响应式断点、改动交互请求链路时，覆盖对应视口、滚动与操作链路；**纯局部字段显隐、文案或单行样式微调**（未改滚动容器、布局结构或按钮交互逻辑）只验证目标界面真实展示与基本入口可用，不扩写大批量虚构数据（如 20 条假列表）、多视口滚动矩阵或未触碰的确认弹窗全套重测。
   - **失败判据**：写可观察的目标行为结果（针对基线旧行为与正常/常规异常下的真实回归），**不要求把单元测试写成内部实现的形式化证明（不锁死内部异步拦截点位置、内部函数调用次数或组件内部 DOM 子节点结构），也不为源码中不存在的假想写法或系统时钟回拨等多重极端时序巧合单设阻断用例**。
4. **分清两类测试**：
   - 开发侧单元测试：写输入、预期输出、常规边界，开发先把它落实成可运行的测试（见 skill `test-first-evidence`），不预设具体夹具实现细节。
   - 最终自动化验收：写用户操作和可观察结果，代码评审通过后由测试人员在真实环境执行（见 skill `real-browser-acceptance`）。
5. **落盘**。用例文件用 `.md`，连同能提前写的自动化脚本一起落盘，写明运行命令和环境，只列直接相关的测试文件或目录，不写全量套件。

完成标准：每条验收标准至少有一条用例，每条用例的字段都填了，失败判据能区分真通过和假通过。

步骤或子 issue 继承根需求已评审的用例，只补必要的定向断言，不重写整份用例。

## 评审用例

逐条核对，结论写「通过」或「需修改」，并列出问题：

- **覆盖**：每条验收标准（有方案时含 spec）都有用例，覆盖主路径与常规异常回归。
- **假通过**：失败判据能否让基线旧行为或真实错误实现失败；有没有永远会过的断言或 mock。不为源码中不存在的假设性写法、内部异步卡点/调用次数偏好或多重极端时序巧合退回用例。
- **不过度加码**：未把 `default: false` 的站点无授权拉入必测，未对纯局部显隐/文案微调强加大批量虚构数据与多视口全套重测，也未要求单测锁死内部实现细节。
- **可复现**：前置条件、数据造法、操作步骤是否足够让别人照做。
- **清理安全**：造数和清理会不会破坏共用数据或别人的环境。

非严重的补充意见单独列出，不阻断开发；仍会假通过、无法验证或会破坏数据的缺口算严重，写明最小修正项。
