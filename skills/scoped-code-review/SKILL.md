# 有界代码评审

评审只回答一件事：这份 diff 有没有满足验收、有没有带进严重问题。范围、预算和停止条件都事先定好，每条验收有结论就收，不把评审做成「顺便把整个模块再看一遍」。

先确定这次是哪种：

- **常规评审**：第一次看这份 diff，或触发升级后重开完整评审。
- **回改核验**：只看 `上次已审版本..当前版本` 的增量和受影响的调用链。

## 范围与预算

- 范围是派活给的 `review-files.json` / 冻结 diff，加上确认候选问题必需的直接调用方、被调用方和相关测试。每个复核项对应一条验收标准或一个具体风险。
- 不在本轮展开、只列入 out-of-scope 的：无关模块、既有基线失败、通用测试债务、无关重构、没要求的生产 GUI / 数据库验收。基线失败单独归因，不重跑全量套件，也不把红灯记成绿。
- 默认预算 20 分钟 / 30 次工具调用；派活写了别的预算就以派活为准。diff 超过 20 个文件或 100KB，要求拆成两段或明确上调预算。用到 70% 仍没收敛，先输出已有候选问题并停止扩展，由派活人决定是否追加。

## 常规评审步骤

1. **先看真实 diff 与验收覆盖**。逐条验收标准判断实现是否满足、测试是否覆盖。只为确认候选问题才展开调用链、异常与状态路径、测试缺口。有 precheck 证据表时，先独立列出严重项，再读 precheck。
2. **核对测试先行证据**。首次开发的独立核验切片核对实现前放行记录；自核切片与评审/测试回改的单趟闭环切片，按 skill `test-first-evidence`「核验者」的标准判断回改前红证据算不算有效失败，无效就判需修改，要求在对应实现前的源码上重新红跑。所有切片都核对红跑、绿跑的 `run.json`、源码快照、原始输出：源码指纹匹配、`source_unchanged` 为 `true`、测试退出码与输出一致、单元测试先于对应实现、没有删改既有通过回归断言或为过测弱化已批准用例（开发者当场修正本轮新写单测自身的夹具/种子错误并在实现前基线重取有效红证属于合法准备修复，无需额外审批记录）。缺证或未经批准弱化通过标准就退回，「现在全绿」不能代替。判断标准见 skill `test-first-evidence`「核验者」一节。
3. **单测断言的阻断边界（禁止死抠内部实现与假想反例）**。当生产代码已正确满足验收标准，且单测已在实现前基线源码上取得有效失败（红）、在交付源码上通过（绿）时，只要断言验证了目标行为结果（界面展示/文案/状态正确、目标数据持久化或锁交接结果正确、原有交互未受损），即判测试覆盖合格。**不得**脑补当前源码与基线源码中均不存在的假设性错误写法，也**不得**强求单测把单元测试写成内部形式化证明（如强求锁死内部异步门控拦截在哪一行、内部函数调用次数、内部 DOM 子节点结构、特定外层挂载路径，或强求造极端时钟回拨夹具）来判阻断、要求补断言或重跑红绿留证。单测仅在「拦不住基线原有旧行为（假红/永真断言）」「漏放当前源码中正常或验收场景真实存在的生产缺陷」或「漏测需求明确点名的业务分支」时才构成阻断。
4. **分级**。阻断和高风险影响结论；建议、验证缺口、out-of-scope 单独列出，不扩大范围。第 1 轮必须把当前 diff 范围内可见的阻断项一次列全，不在后续回改复核中对未改动部分追加首轮就存在的新挑刺。
5. **停止**。每条验收标准都有结论、且没有新的阻断候选就停，不为「确认」重复读同一文件或复查同一问题。发现阻断先报告，再决定要不要查下一项。

### 严重与非严重

按真实可触发性与影响判断，不只看 P0/P1 或理论推导终点。

- **严重**：在正常用户操作、本需求明确场景或常规异常（如普通断网、普通刷新/关页、接口报错）下可稳定或高概率触发的核心验收不满足、数据丢失、越权、安全漏洞、把基线旧代码或当前真实缺陷漏判成通过、改变未授权的生产语义、不可回滚的破坏、阻塞后续全部验证。
- **非严重**：审美、命名、低风险整理、可延后的优化、针对源码中不存在写法的防御性断言补充，以及**需要多重极端时序或环境巧合叠加才能触发的理论边界加固**（如操作系统时钟突然回拨、毫秒级异步销毁间隙恰好切换上下文且未换对象、两个独立子系统在同一瞬间发生方向相反的故障）。在正常操作与验收场景已闭环时，这类极端边界一律归入非严重建议（逐条写来源步骤、代码位置、影响、建议，不阻断后续测试），**不得**仅因“理论上往下推可能影响状态/锁”就升级为阻断。与本需求无关的发现单独列出，交派活人登记。

## 回改核验步骤

1. 按问题 ID、验收条件、上次已审 SHA，核验上次未过项是否已关闭、本次增量 diff 是否在正常或验收场景下引入必现/高概率回归（如改过滤逻辑误伤普通路径），以及本轮单趟红绿留证是否完整有效。实现者自报「已修」不算关闭；**不在回改核验中顺调用链无限外推低概率理论边界**。
2. 证据不足、上次严重问题未消除、引入新的严重回归或测试版本与交付版本不一致，一律不放行。当派活写明已达回改核验轮数上限、核对架构师唯一最终收口裁定时，**只核对架构师点名的改法是否落实，严禁再提出任何新阻断项**。
3. 每次回改结论必须写一行：**「是否碰到关键决定 / 方案取舍 / 验收口径：是/否 + 依据」**。仅当既有关键决定、方案取舍或验收口径本身需要推翻或重定方向时才写「是」交架构师裁决；遵循既有裁定修复局部实现遗漏一律写「否」，不反复升级。
4. 以下任一情况也写明「需升级」：推翻了架构师的关键判断；改变核心契约、安全边界或关键不变量；扩散到没覆盖过的重要模块；修复证据互相冲突。

## 输出

- 结论对应具体版本（SHA）。阻断/高风险、非严重、验证缺口、out-of-scope 分开列。
- 在 team-up 交付中，结尾单独一行写 `常规评审通过` 或 `常规评审需修改`（回改核验同样），用户可见的结论按派活要求分「## 给用户的摘要」和「## 完整内容」两个二级标题。常规评审通过不等于最终放行，最终放行由架构师风险终审决定。
