# 测试先行留证与核验

先让测试因为「功能还没做 / 缺陷还在」而真实失败（红），确认这次失败算数，才写实现，最后再跑一次通过（绿）。首次开发的高风险切片由另一个人核验后放行；其余首次切片与后续评审/测试回改切片，由开发者按同一标准自核有效失败后在同一趟直接实现并绿跑，交代码评审或回改核验一并核对。哪种由派活写明（team-up 里见协议 implementation §6「实现前检查点」「回改打包」）。这样既能证明测试真能抓到问题、实现没有靠改测试过关，又避免小返工来回拆步排队。

按**行为切片**推进：一个能单独验证的行为走一遍「写测试 → 红跑 → 核验或自核 → 实现 → 绿跑」。不按每条断言各走一遍，也不先写完整实现再补测试。

## 开发者：每个切片的步骤

1. **写测试**。按已评审的验收用例（debug 按 issue 验收点，回改按评审/测试指出的问题）新增或补充定向单测，已有测试覆盖就直接复用。完成标准：测试文件落盘，能指出目标断言的文件和行号。
2. **红跑留证**。对应生产代码还没改时，用下方「留证命令」跑一次 `--phase red`。完成标准：目标断言因为功能没做或缺陷还在而失败。
   - 环境、依赖、语法、导入、编译错误不算有效失败，先修测试准备再重跑。接口或模块还不存在导致到不了断言时，调整测试边界；确实到不了就交核验者判断验证方式，不加生产占位实现绕过。
   - 跑出来已经通过：先查是不是无需改代码或选错了测试，不故意破坏实现造红。
   - 保持既有行为的改造：用通过的测试锁定行为，写明为什么不需要新增失败。纯文档等没有可单测行为的改动：写明原因和替代检查。首次开发中这两类交核验者确认，不自行免测。
3. **交接或自核**。准备证据目录（`run.json`、`output.log`、源码快照）、测试文件、目标断言位置，以及「期望什么、实际什么、为什么是目标功能导致失败」。
   - 派活写「独立核验」的首次开发切片：拿到核验者的「允许实现」之前，不编辑对应生产代码。等待期间可以接着写下一个切片的测试并红跑，但不碰任何未放行切片的生产代码。
   - 派活写「自核」的首次切片，或评审/测试后的「回改单趟闭环」切片：按下方「核验者」的标准逐条自查，确认红证有效后直接进入第 4 步修改生产代码并绿跑，最后把回改前红证、回改后绿证与代码增量在同一次交接中一并提交。自查不过就先在未改生产代码基线上修好测试准备重取红证，不带着无效红证据改生产代码。
4. **实现并绿跑**。只改实现让已确认的测试通过，用新的证据目录跑 `--phase green`，再跑相关单测、lint、type-check。只跑直接相关的测试，不跑全量。
5. **交付**。交 HEAD/diff、红跑和绿跑证据目录、放行记录路径（首次独立核验切片）或自核说明、命令与结果、未验证项。缺红跑证据不能称完成。

### 测试本身写错了

失败先查实现。不为过测改预期、放宽断言、删除或跳过既有通过回归用例、用必过的 mock 代替真实逻辑、更新快照迎合错误。

- **本轮新增单测自身的夹具/种子准备有误**（例如本轮新写的测试手填序号撞号、模拟初始状态漏配无关前置字段导致误红或阻碍测试运行，且不涉及删改既有通过回归断言或降低已批准验收标准）：开发者直接修正该夹具准备，退回本次生产修改前的源码基线重新取得有效 `--phase red` 证据，再在修复代码上跑 `--phase green`，在交接中如实注明夹具修正原因，**无需停下申请独立审批**。
- **已批准的验收用例文档或既有通过的回归断言本身有误**：先停对应实现，交出验收依据、原断言、失败输出、拟改内容和理由，由独立核验者复核；验收口径或需求变了，交给有权裁定的人（在 team-up 里按派活人的指示）。批准后才改，保留前后版本和审批记录，并重新取得有效红证据。已上传的评审文档变了，要同步更新。

### 发现已经先写了实现

立即停下这个切片，保留代码、日志和事实，不删历史、不倒退重跑冒充先行。可以补测试验证当前行为，但历史缺证仍然算缺，要如实报告，等有权的人给例外授权。

## 核验者：判断这次失败算不算数

只核这个切片：验收条目、测试、红跑日志、实现前源码。不做整项代码评审。

有效失败必须**同时**满足：

- 测试被成功收集并进入了目标断言；
- 失败原因证明功能没做或缺陷还在；
- 没有夹具、依赖、语法、导入、权限、服务故障遮住结果；
- `run.json` 里留证脚本无错，`source_unchanged` 为 `true`；
- 真实退出码非零，且与 `output.log` 一致；
- 源码快照证明当时生产代码还没改。

`--phase red`、非零退出码或日志里有 FAIL，都不能单独作依据。

首次独立核验切片在任务的 `reviews/` 目录留一份记录：验收编号、测试与源码指纹、证据路径、失败断言、结论（只写「允许实现」或「先修测试准备」）；自核与回改切片在代码评审/回改核验中按同一标准合并给出结论。保持既有行为、纯文档等例外，也按此核验理由和替代证据。

只要目标断言已在实现前真实基线源码上因功能未做/缺陷仍在而稳定失败，就满足先行证明；**不得**脑补当前源码与基线源码中均不存在的假想写法，也**不得**把单测当成内部形式化证明去挑剔内部异步门控停在哪一个子调用、未断言内部函数调用次数、未穷举内部中间状态、未锁死内部 DOM 节点树结构或未走特定外层挂载入口来判「先修测试准备」。

判「先修测试准备」时，一次列出这个切片的全部问题，每条写清改什么、改成什么样算过；不要留到下一轮再提新问题。复核时只核上次列出的问题有没有改好，以及这次改动有没有带进新问题。

## 留证命令

每次红跑、绿跑都用这个脚本，不手拼命令，不只交日志或最终提交号：

```bash
python3 ~/.hwf/scripts/test-evidence.py \
  --repo <被测仓库根目录> --out <每次运行独占的新证据目录> \
  --case <验收编号> --phase red \
  -- go test ./internal/service -run '^TestTargetBehavior$' -count=1
```

- `--` 后面直接写测试程序和参数，不包 `sh -c`，不接管道、`; tail`、`; echo`，否则拿到的是外层命令的退出码。日志另读 `output.log`。整个进程失败，不能因为某个用例 PASS 就算绿。
- 脚本跑测试前保存 `source.json`（全仓跟踪文件与未忽略新文件的 SHA-256 指纹及删除记录）、`dirty.tar`（仅打包相对 HEAD 有改动或新增的工作树文件与符号链接，不重复复制整仓未改文件）、HEAD、暂存和未暂存补丁、Git 状态；跑完在内存中复核全仓指纹并把原始输出、真实退出码、起止时间和源码是否变化写进 `run.json`。需要还原当时完整源码时运行 `python3 ~/.hwf/scripts/test-evidence.py --restore <证据目录> --to <新建的空目录>`，不覆盖工作树。
- 输出目录在团队流程中统一放在 `<主仓库>/.hwf/tmp/<任务标识>/development/<切片>/`（非团队单次任务放 `<仓库根目录>/.tmp/evidence/<切片>/`），已有目录会被拒绝；**严禁**在仓库或 worktree 根目录直接新建顶层 `evidence/`、`testing/` 目录，也不得改仓库 `.gitignore` 遮盖误放产物。快照不含 `.git` 和被忽略的依赖、本地配置，也不保证能重建外部服务；有子模块时脚本拒绝运行，要对子模块仓库单独取证。
- 测试期间独占工作树，不并行改源码。前后源码或 HEAD 变了，证据无效，退出码 125。信号终止映射为 `128 + 信号号`。
- 快照和日志可能含敏感信息：只存在任务授权的本地目录，不直接上传 GitLab；凭据不放在命令参数里。事后重跑不能补齐历史上缺失的先行证据。
